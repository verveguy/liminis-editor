# ADR-088: The Document Outline Widget Stays Host-Seam-Free and Is Wired Through a Shared Controller Object, Not a Ref

**Date:** 2026-08-18
**Status:** Accepted
**Supersedes:** none
**Amends:** none
**Issue:** #69 (verveguy/liminis-editor)

## Context

`liminis-app`'s table-of-contents widget — heading list, click-to-scroll,
scroll-spy — lived entirely in the app, duplicated its click-to-scroll logic
across two call sites, and hardcoded two different scroll-container ids
between them (`editor-panel-scroll-container` in one, `editor-scroll-container`
in the other). Extracting it into `@liminis/editor` as a considered export
(FR-001) raised two design questions the issue's own research flagged as
needing a deliberate answer rather than an implicit one:

1. **FR-006** requires the widget not hardcode a host DOM id or assume a
   specific scroll container, and says the scroll container/element
   positions "MUST reach it through the editor-host seam (or be owned by the
   package)". `AnchorScrollPlugin` — an existing plugin that scrolls the
   editor to an anchor-linked heading — already solves exactly this problem
   package-locally: it tries the two known host ids, then walks DOM
   ancestors for the nearest actually-scrolling one, with no
   `EditorHostServices` involvement at all. Whether the outline widget should
   reuse that precedent or instead earn `EditorHostServices` a new
   scroll-container/element-rect member was open.

2. `<Editor>` renders a fixed internal plugin list with no slot a consumer
   can render into, and FR-008 requires the widget's placement to be entirely
   the consumer's decision — so the rendered list cannot simply be "a child
   of `<Editor>`" the way `AnchorScrollPlugin` is. It has to be a separate,
   freely-placed component, while the data it renders and the scroll-to
   action it triggers live inside the Lexical tree `<Editor>` owns. How those
   two pieces communicate — a component mounted inside `LexicalComposer`
   feeding data out, and a component mounted anywhere reading it back in —
   was undecided. The package's one existing precedent for "read the live
   editor from outside `<Editor>`", `annotationEditorHandleRef`, is a
   `MutableRefObject` populated after mount and read imperatively later. That
   doesn't fit here: the outline component has to *reactively* re-render on
   every scroll and edit, and mutating a ref's `.current` does not notify a
   sibling component holding the same ref.

## Decision

**No new `EditorHostServices` member.** The outline widget's scroll-spy and
scroll-to-heading logic reuse `AnchorScrollPlugin`'s container-discovery
logic directly — extracted, as a pure refactor, into a shared
`src/app/editor/scrollContainer.ts` (`scrollContainerFor()`,
`scrollElementIntoView()`) rather than duplicated. FR-006's own text permits
this explicitly ("... or be owned by the package"), and the only named
beneficiary of a shared host-seam capability for scroll-container/element-rect
data — Zusammen issue #126, margin comments aligned to text — is not yet
planned. Building a generalized host-seam primitive now, for a consumer that
doesn't exist yet, would be speculative and untested; `scrollContainer.ts` is
deliberately factored out so that whenever #126 does start, it has a single,
already-proven extraction point to build from instead of a second
copy-pasted implementation.

**A shared controller object connects `<Editor>` to the outline component,
not a ref.** `createDocumentOutlineHandle()` returns a `DocumentOutlineHandle`
— a React external store (`subscribe`/`getSnapshot`, consumed with
`useSyncExternalStore`) plus an imperative `scrollToHeading(index)`. The
consumer creates one per editor instance and passes the *same* object to both
`<Editor documentOutlineHandle={handle}>` and
`<DocumentOutline handle={handle}>`. Internally, an `OutlinePlugin` — mounted
inside `<Editor>`'s `LexicalComposer` tree only when `documentOutlineHandle`
is supplied, so an outline-less consumer pays nothing for it — walks
`HeadingNode`s on every `registerUpdateListener` firing to populate entries,
runs an rAF-throttled scroll-spy scoped to `editor.getRootElement()`'s
`.editor-heading-hN` elements, and implements `scrollToHeading` by reusing
`scrollElementIntoView`. `<DocumentOutline>` never talks to Lexical directly;
it only reads the handle.

Because the handle is created per call site rather than shared globally, an
outline for one editor instance can never aggregate headings from a second,
simultaneously-mounted editor — the correctness gap `EditorColumn`'s current
`document.querySelectorAll`-based implementation has today, closed as a
side effect of this shape rather than as a separate fix.

Entries are derived from **live Lexical state**
(`HeadingNode.getTextContent()`), not by re-parsing the markdown string:
`getTextContent()` already reduces inline content — including inline code —
to plain text, matching FR-002 without a second parse pass, and the same
update listener that populates entries already satisfies FR-005 (the
outline stays current) with no extra staleness tracking.

## Consequences

**Good:**

- FR-006 is satisfied with zero new, untested API surface. `AnchorScrollPlugin`
  already demonstrated the DOM-ancestor-walk approach works and is exercised
  by `host-plugins.test.tsx`; the outline widget inherits that coverage
  rather than duplicating the risk with a second implementation.
- `scrollContainer.ts` is a real extraction, not a footnote: both
  `AnchorScrollPlugin` and `OutlinePlugin` call the same functions, so a fix
  to the container-discovery heuristic fixes both at once, and Zusammen #126
  has a concrete starting point instead of a green-field design.
- The handle-sharing pattern gives `<DocumentOutline>` true placement freedom
  (FR-008) — it can render anywhere, including outside `<Editor>`'s own
  subtree — while still reacting live to scroll and edits, which a
  `MutableRefObject` cannot do for a sibling reader.
- Multi-editor correctness (no cross-instance heading aggregation) falls out
  of the design for free, rather than requiring a scoping fix bolted on
  afterward.

**Bad / accepted:**

- The DOM-ancestor-walk heuristic — "nearest ancestor with `overflow-y:
  auto|scroll` and real overflow" — is inherited, not newly assessed; an
  unusual host layout could still pick the wrong container. This was already
  an accepted risk for `AnchorScrollPlugin` before this issue.
- The handle-sharing shape (`documentOutlineHandle` prop shared between
  `<Editor>` and a sibling component) is new API surface with no prior
  precedent in this package — annotations use a ref instead — so it is the
  first place a consumer has to learn this particular pattern.

**Neutral:**

- Extending `EditorHostServices` for scroll-container/element-rect data was
  considered and explicitly deferred, not rejected outright — see Zusammen
  #126. If and when that issue lands, `scrollContainer.ts`'s functions are
  the natural seed for whatever host-seam capability it needs, rather than a
  redesign from scratch.
