# ADR-048: Programmatic MCP Server Loading — Empty .mcp.json (2026-03-23)

> Extends [ADR-043](./adr-043.md) (Stdio Proxy MCP Wrappers) and [ADR-037](./adr-037.md) (In-Process MCP Wrappers)

**Context:**
- The Claude Agent SDK reads `.mcp.json` via `settingSources: ['project']` and independently connects to every MCP server listed there
- The Liminis app also programmatically builds MCP server configs in `claude-agent.ts` and passes them via the `mcpServers` parameter to the SDK's `query()` call
- Over time, ALL server types migrated to programmatic loading via in-process proxies:
  - **Stdio servers** (knowledge-reader, knowledge-writer, semantic-search): Dynamic stdio proxies forward through `McpDirectInvoker` (ADR-043)
  - **OAuth HTTP servers** (confluence, github): HTTP proxies with token injection (ADR-043 pattern)
  - **In-process servers** (workflow, actions, liminis-app): Created directly as callback servers
- This made `.mcp.json` fully redundant — every server in it was already loaded programmatically
- Worse, the SDK's independent loading of `.mcp.json` created **duplicate server instances** for any server listed there, defeating the proxy architecture's single-instance guarantee
- The `regenerateRuntimeConfig()` function had accumulated workarounds: omitting OAuth servers, omitting disabled servers — all to prevent SDK double-loading. But stdio servers (knowledge-reader, etc.) were still in `.mcp.json` and loaded by the SDK independently of the proxies
- This also blocked service quiescing during framework upgrades: even when `mcpServers: {}` was passed programmatically, the SDK still loaded servers from `.mcp.json`

**Decision:**
Write an **empty `.mcp.json`** (`{ "mcpServers": {} }`) so the SDK finds no servers to load independently. All MCP servers are loaded exclusively through the programmatic `mcpServers` parameter.

The previous `regenerateRuntimeConfig()` implementation that populated `.mcp.json` from the composed config is preserved as commented-out code for rollback safety.

**Implementation:**

| Component | Change |
|-----------|--------|
| `src/main/mcp-config/index.ts` | `regenerateRuntimeConfig()` now writes empty `{ mcpServers: {} }` |
| `src/main/claude-agent.ts` | No change — already builds all servers programmatically |
| `.mcp.json` (workspace) | Now always empty — SDK finds no servers to load independently |

**Why `settingSources: ['project']` is kept:**
The `settingSources` option controls loading of ALL project settings: CLAUDE.md, `.claude/settings.json`, `.claude/rules/*.md`, AND `.mcp.json`. We can't selectively exclude `.mcp.json` — it's a single flag. Writing an empty `.mcp.json` achieves the same effect without losing the other project settings.

**Service quiescing benefit:**
When services are quiesced for framework upgrades, `mcpDirectInvoker.isQuiesced` causes `claude-agent.ts` to pass `mcpServers: {}`. With `.mcp.json` also empty, the merge agent runs with zero MCP servers — exactly the desired behavior during upgrades.

**Consequences:**
- ✅ Single source of truth for MCP server loading: `claude-agent.ts` programmatic config
- ✅ No duplicate server instances from SDK's independent `.mcp.json` reading
- ✅ Service quiescing works correctly — empty `mcpServers` means no servers
- ✅ Eliminates all the workarounds in `regenerateRuntimeConfig()` (omitting OAuth, disabled, etc.)
- ✅ `.mcp.json` still exists (SDK expects it), just empty
- ⚠️ Running `claude` CLI directly in the workspace (outside the app) won't see MCP servers — this is acceptable since the CLI isn't the primary interface
