# ADR-056: Unified Search with Reciprocal Rank Fusion (RRF) (2026-04-22)

**Context:**
- Cmd-K previously concatenated two retrievers (text via `search:notes`, vector via `search:semantic`) and sorted by raw score. Raw scores were not directly comparable across backends, passages found by both backends surfaced twice (deduplicated only by file path), and the graph signal (entities, relationships) was not used at all.
- The post-LEANN context graph stack (ADR-035, ADR-042, ADR-051, ADR-052) consolidated all retrievers behind one engine, making cross-retriever fusion feasible at the app layer.
- Cormack et al.'s Reciprocal Rank Fusion (RRF, 2009) is the standard choice for combining ranked lists where score calibration is impractical — exactly the shape of the cmd-K problem.

**Decision:**

Fan cmd-K queries out to three conceptual retrievers, fuse their ranked lists via RRF in the main process, and return a single heterogeneous result list to the renderer.

### Orchestration layer

- **App-layer orchestration.** A new `search:unified` IPC handler in the main process owns fan-out, RRF fusion, and result typing. The alternative (a composite MCP tool wrapping Graphiti's internal `search()`) was rejected because the Python reader server lives in the upstream graphiti framework package, not in this repo — adding a tool there would block landing the feature.
- `search:semantic` is removed (only cmd-K used it). `search:notes` stays and is called first from the renderer so text hits render immediately while the serialized context graph chain runs, preserving the "feels fast" progressive UX.

### Retrievers

1. **Text** — `fs.searchNotes` (substring over markdown, unchanged). Runs in parallel with the context graph chain.
2. **Context graph reader chain** — serialized because `mcp-direct-invoker` rejects concurrent calls to the same stdio server (ADR-042):
   1. `knowledge_search_passages` — vector-retrieved passages (Episodic content embeddings).
   2. `knowledge_find_entities` — entity matches.
   3. `knowledge_get_entity_neighbors` — called with the **top-ranked entity's UUID** to derive facts (edges) relevant to the query.

Total reader-server calls per query: three, summing to ~360ms on typical hardware — under the 500ms target. When the context graph is unavailable or busy the handler returns text-only results (graceful degradation).

### Fact derivation

The spec assumed a `knowledge_find_relationships` tool exists on the reader server; in fact it does not — the reader exposes only `knowledge_list_relationships` (a full dump). Research explored three options:
- (a) Add the tool upstream — cross-repo, blocks landing.
- (b) Filter `knowledge_list_relationships` client-side — cheap but low-signal.
- (c) Expand from the top-ranked entity's neighbors.

We chose (c). It meets the "passages AND entities AND facts" success criterion, requires no upstream work, and reuses `knowledge_get_entity_neighbors`'s ADR-040 edge-direction correction for free. A future upstream `knowledge_find_relationships` tool can replace this step.

### Fusion

Standard RRF: each candidate accumulates `1 / (60 + rank_i)` across every list it appears in, with `k = 60` (the canonical value). Ties break by (1) number of contributing retrievers, then (2) retriever order in the input lists.

Deduplication is *within-kind only*:
- Passages key on `path` (text and vector hits on the same file fuse).
- Entities key on context graph entity UUID.
- Facts key on context graph edge UUID.

Cross-kind dedup is intentionally *not* applied: a passage mentioning an entity is a different answer shape by design and the user should see both.

### Result type

A discriminated union on `kind`, defined in `src/shared/unified-search-types.ts` so both main and renderer can import it without crossing project boundaries:

```ts
type UnifiedSearchResult =
  | { kind: 'passage'; path; title?; section?; snippet; matchIndex?; …; sources: UnifiedResultSource[] }
  | { kind: 'entity'; uuid; name; entityType?; summary; linkedEpisodePaths; sources: UnifiedResultSource[] }
  | { kind: 'fact'; uuid; subject; predicate; object; factText; sourceEpisodePaths; sources: UnifiedResultSource[] }
```

Payload caps: entity summary ≤ 300 chars; linked-episode / source-episode arrays ≤ 5.

### Selection UX

- **Passage** — open file, scroll to match (existing behavior via `handleFileSelect` + the `slashmd:search` editor command).
- **Entity** — toggle an inline expansion underneath the row showing name, type, summary, and clickable episode chips that open the underlying file. Escape collapses the expansion before closing the dialog.
- **Fact** — toggle an inline expansion showing `subject — predicate → object`, the fact text, and clickable source-episode chips.

Keyboard: Enter toggles expansion for entity/fact rows and opens the file for passage rows. Escape collapses any open expansion before closing the dialog.

**Alternatives Considered:**
- **Composite MCP tool wrapping `graphiti_core.search.search`** — cleanest long-term but cross-repo. Deferred until the multi-retriever workload justifies the upstream work.
- **Query-shape routing (BM25-weighted for quoted strings, graph-weighted for questions)** — deferred to v2 if equal-weight RRF proves insufficient.
- **Server-side queue in `mcp-direct-invoker`** — would let the three context graph calls run without serialization changes in each handler, but rewrites a load-bearing concurrency contract used everywhere. Out of scope.
- **Streaming IPC (multiple `onResults` emits from main)** — rejected; progressive UX is preserved via the simpler "call `search:notes` then `search:unified`" pattern in the renderer.

**Consequences:**
- ✅ Graph entities and facts appear in cmd-K for the first time.
- ✅ Text + vector passages on the same file surface once, boosted by dual contribution.
- ✅ Result scores are comparable (fused RRF score) rather than raw BM25 vs cosine.
- ✅ Graceful degradation: context graph down ⇒ text-only results, same UX as pre-RRF.
- ❌ Context graph critical path is serialized (3 calls × ~120ms). Latency budget is tighter than the prior two-retriever design.
- ❌ Facts are an approximation — neighbors of the top-ranked entity, not a direct relationship search. Coverage drops when the top entity is weakly connected.
- ❌ No main-process cancellation on new keystrokes; renderer debounce (400ms) is the only backpressure.
