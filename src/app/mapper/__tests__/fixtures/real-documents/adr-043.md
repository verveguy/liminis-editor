# ADR-043: Stdio Proxy MCP Wrappers — Dynamic Tool Discovery (2026-03-02)

> Supersedes ADR-037 (In-Process MCP Wrappers for Claude Agent SDK)

**Context:**
- ADR-037 introduced in-process MCP wrappers to solve the dual-instance problem: the Claude Agent SDK spawns its own stdio process for each MCP server, conflicting with the app's long-lived instances managed by `McpDirectInvoker`
- The ADR-037 solution worked but required **manually duplicating every tool schema** in TypeScript/Zod, mirroring the Python server's definitions
- With 18 knowledge graph tools (reader + writer) and 9 semantic search tools, this created a significant maintenance burden — every tool addition or schema change in Python required a matching TypeScript update
- ADR-037 explicitly acknowledged this: "Tool schemas must be manually kept in sync with Python server definitions"
- Meanwhile, the HTTP proxy pattern (`createHttpProxyMcpServer`) built for OAuth MCP servers already solved this by dynamically discovering tools via `tools/list` — the same approach could work for local stdio servers

**Decision:**
Replace the per-server static Zod wrappers with a single generic factory, `createStdioProxyMcpServer()`, that dynamically discovers tools from the real stdio server at startup.

```
Claude Agent SDK
  → stdio proxy (callback server, no child process)
    → mcpDirectInvoker.listTools(serverName)    // discover tools at startup
    → mcpDirectInvoker.callTool(name, tool, args) // forward each call
      → single stdio MCP server (managed by app)
```

The factory:
1. Calls `mcpDirectInvoker.listTools(serverName)` to get tool names, descriptions, and JSON schemas
2. Maps each tool to an SDK tool definition with **schema shimming** — raw JSON Schema objects augmented with `safeParseAsync`/`safeParse` passthrough methods so the SDK's internal Zod validation doesn't reject them
3. Each tool handler calls `mcpDirectInvoker.callTool()` and wraps the result into the SDK's `CallToolResult` format
4. Returns `createSdkMcpServer({ name, version, tools })` — a callback-based server with no child process

**Implementation:**

| File | Purpose |
|------|---------|
| `src/main/mcp-stdio-proxy-server.ts` | Generic factory — one file replaces three wrappers |
| `src/main/claude-agent.ts` | Creates proxies via `Promise.all` at session start |

Deleted files (replaced by the proxy):
- `src/main/graphiti-reader-mcp-server.ts`
- `src/main/graphiti-writer-mcp-server.ts`
- `src/main/semantic-search-mcp-server.ts`

**Schema shimming pattern:**

The SDK expects Zod-like schemas with `.safeParseAsync()` and `.safeParse()` methods. The proxy attaches passthrough shims to the raw JSON Schema so validation always succeeds at the proxy layer — the real Python server validates inputs server-side:

```typescript
inputSchema: Object.assign({}, remoteTool.inputSchema, {
  safeParseAsync: async (data: unknown) => ({ success: true, data }),
  safeParse: (data: unknown) => ({ success: true, data }),
})
```

This is the same pattern used by `createHttpProxyMcpServer()` for OAuth servers.

**When to apply this pattern:**
- Same criteria as ADR-037: the app manages a long-lived stdio server that also appears in SDK config
- The server uses exclusive resources (ports, locks) or maintains state the app updates
- **Prefer this over static wrappers** unless you need TypeScript-level input validation before forwarding

**Alternatives Considered:**
- **Keep static Zod wrappers (ADR-037)** → Rejected: schema sync burden grows with every tool addition; three files deleted, 324 net lines removed
- **Code generation from Python schemas** → Rejected: adds build-time complexity, CI dependency on Python environment, still requires regeneration on changes
- **Shared JSON Schema files imported by both Python and TypeScript** → Rejected: runtime discovery is simpler and requires no shared artifact management
- **Have the SDK connect to existing server process** → Still not supported by the SDK (same as ADR-037)

**Consequences:**
- ✅ Python servers are the **single source of truth** for tool names, schemas, and descriptions
- ✅ Adding or modifying tools in Python requires **zero TypeScript changes**
- ✅ Single generic factory replaces N per-server wrapper files (-324 net lines)
- ✅ Same forwarding architecture as ADR-037 — no resource conflicts, agent sees fresh data
- ✅ Consistent with HTTP proxy pattern — both use schema shimming and dynamic discovery
- ⚠️ Slight startup latency: must call `listTools()` before agent session begins (parallelized via `Promise.all`)
- ⚠️ Less compile-time type safety at the proxy boundary (accepted: Python server validates, and tools change infrequently)
- ⚠️ If a stdio server fails to start, proxy creation fails gracefully (logged warning, server omitted from session)

**Long-running maintenance operations (`callServiceCommand` / `callTool`):**

App-only maintenance operations that can run longer than 5 minutes must pass `killOnTimeout: false` in their call options regardless of whether they use `callServiceCommand` (→ `service/call` RPC) or `callTool` (→ `tools/call` RPC):

```typescript
// service/call RPC — e.g. knowledge_rebuild_from_wal
await mcpDirectInvoker.callServiceCommand(
  KNOWLEDGE_WRITER, 'knowledge_rebuild_from_wal', {},
  { timeoutMs: 3_600_000, killOnTimeout: false }
)

// tools/call RPC — e.g. knowledge_reprocess_entity_types
await mcpDirectInvoker.callTool(
  KNOWLEDGE_WRITER, 'knowledge_reprocess_entity_types', {},
  { timeoutMs: 3_600_000, killOnTimeout: false }
)
```

Without `killOnTimeout: false`, a timeout fires `entry.client.disconnect()` which kills the server mid-operation — causing cascading UI failures (false "Connection error", zero entity/episode counts). With `killOnTimeout: false`, the timeout still returns an error to the caller, but the server process is left alive to finish and accept subsequent calls. Opt-out timeouts are also excluded from the `consecutiveFailures` counter, so the server entry is not incorrectly marked permanently failed. The kill-on-timeout behavior is preserved for all ordinary calls that do not pass this flag.
