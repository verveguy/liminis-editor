# ADR-059: Workspace-Readiness Lifecycle Gate (2026-04-26)

**Context:**

- Before this change, `createWindow()` in `src/main/index.ts` started every workspace-bound service the moment `workspaceRoot` was non-null. `registerAllServices` + `registry.startAll()` (per ADR-053) fired immediately, alongside `scheduledTaskManager.start`, the indexing queue load + watcher action-items callback, the remote-session HTTP server, and `initRemarkableSyncWatcher`. None of these checked whether the workspace had actually completed onboarding.
- On first run, the framework download happens *later* — inside the renderer's `SetupWizard` — so workspace-bound services raced the framework install:
  - `context-graph-service` spawned `uv run graphiti_service.py` against a workspace whose `.claude/skills/graphiti/` did not exist yet.
  - `mcp:semantic-search` spawned `uv run server.py` against a missing `.claude/skills/semantic-search/scripts/server.py`.
  - The file watcher's action-items callback ran `runActionItemsScript` (`uv run .claude/skills/action-items/scripts/action_items.py`) as the framework downloader was writing files into the workspace.
- When `uv` was missing from the Electron PATH (common on macOS — GUI apps do not inherit shell PATH, so `~/.local/bin`, `/opt/homebrew/bin`, `~/.cargo/bin` are invisible), spawn yielded ENOENT, which until very recently bubbled up as `Uncaught Exception: Error: spawn uv ENOENT` in the main process. Even after the listener-ordering mitigation in `context-graph-lifecycle.ts:365` and `mcp-direct-invoker.ts:220`, the underlying race produced a flurry of script-not-found / wrong-state failures and tripped the context graph's auto-restart loop (`MAX_CONSECUTIVE_CRASHES`) before the workspace was ready.
- A `setup_complete` sentinel had existed in `.liminis/` for some time (written by `writeSetupCompleteFile()` in `workspace-init.ts`), but nothing in the service-startup path read it. It existed only as a signal to the AI/setup-skill that "you're done."
- `workspace:initialize` and `workspace:installOnboardingComponents` IPC handlers — both invoked by the wizard during onboarding — additionally called `initializeMcpServersWithContextGraph` + `prewarmMcpServers` post-invocation, redundantly racing the registry-driven spawn.

**Decision:**

Layer a **workspace-readiness lifecycle gate** on top of ADR-053's tiered service registry. Split `createWindow()`'s post-`workspaceRoot` block into two phases:

```
no-workspace ──pick──▶ onboarding ──setup_complete written──▶ ready
                          │ (always-on phase only)             │ (workspace-ready phase fires)
                          │                                    ↳ registerAllServices, indexing-queue load,
                          │                                      watcher action-items callback,
                          │                                      scheduledTaskManager.start, remote-session,
                          │                                      remarkable sync
                          ↳ setLogWorkspace, claudeAgent/chatState/notificationManager/historyManager wiring,
                            checkpointRestoration setter
```

- **Always-on phase** runs unconditionally once `workspaceRoot` is known. Pure wiring only: logger, `chatStateManager`, `notificationManager`, `historyManager`, `claudeAgentManager`, `checkpointRestoration` setter. No registry start, no `uv` spawn, no workspace-bound subprocess.
- **Workspace-ready phase** runs only when `isSetupComplete(workspaceRoot)` is true. Encapsulated in a single idempotent helper `runWorkspaceReadyPhase(ctx)` (`src/main/lifecycle/workspace-ready.ts`). Owns `registerAllServices`, `registry.startAll`, indexing queue load + watcher callbacks, `scheduledTaskManager.start`, remote-session server init, `initRemarkableSyncWatcher`. Guarded by a process-level boolean so the second invocation is a no-op.

**Two convergent fire points:**

1. **`createWindow()` at app launch** — when `isSetupComplete(workspaceRoot)` is already true, the phase fires synchronously after always-on wiring. Maintains the no-regression guarantee for established workspaces (no added startup latency, ADR-053 tiering preserved).
2. **`workspace:markSetupComplete` IPC** — fires the phase the first time it is invoked in a process. Subsequent invocations are no-ops because the in-flight promise is cached. The IPC handler captures the dependency context once during always-on (`setPendingWorkspaceReadyContext`) and replays it.

To close the "agent writes the sentinel directly without IPC" gap surfaced in research, the wizard's "Start Using Liminis" button now calls `window.api.workspace.markSetupComplete()` itself before invoking `onComplete()`. The IPC is therefore the canonical first-run trigger.

**In-process MCP wrapper placement heuristic:**

Any in-process MCP wrapper whose tool handlers can reach a `spawn`/`exec` against a workspace-scoped path under `.claude/skills/` registers in the workspace-ready phase. Wrappers that are pure (no workspace-skill dependency) can stay always-on.

Today this rule classifies:
- **Workspace-ready (gated):** `mcp:actions` — every tool reaches `runActionItemsScript` → `uv` against `.claude/skills/action-items/`.
- **Pure (always-on capable):** `mcp:workflow` (in-process JS over `.beads/` files), `mcp:liminis-app` (Node FS / git via `execSync`).

In practice this implementation registers *all* services through `registerAllServices` inside the workspace-ready phase, including the pure ones. ADR-053's `registry.startAll()` is single-shot per process, which makes a partial pre-registration (some services pre-gate, others post-gate) impractical. The renderer-side per-query SDK MCP attachments in `claude-agent.ts` cover the wizard's setup-stage agent's tool surface independently of the registry, and those continue to attach `workflow` and `liminis-app` always (the `actions` server is omitted pre-gate per the heuristic).

**Defensive guards beyond the registry gate:**

- **`actions:*` IPC channels** (`actions:getIndex`, `actions:buildIndex`, `actions:toggleAction`) throw `Error('workspace setup not complete')` when `!isSetupComplete(workspaceRoot)`. These channels are renderer-callable; if the renderer mistakenly invoked one during onboarding it would otherwise spawn `uv`. Throwing (rather than returning a `{ success: false, error }` object) preserves the existing `Promise<void>` / `Promise<ActionIndex>` window-API contract and surfaces failures through the renderer's normal await/try-catch path instead of getting silently dropped at callsites that don't inspect a return value.
- **Per-query agent MCP construction in `claude-agent.ts`** filters out the `actions` server when the gate is closed. The per-query path is independent of the registry, so the gate must be checked there too.
- **`workspace:initialize` and `workspace:installOnboardingComponents` post-invoke service spawn** — `initializeMcpServersWithContextGraph` + `prewarmMcpServers` + watcher restart — is wrapped in `if (isSetupComplete(workspaceRoot)) { ... }`. During first-run those calls are no-ops; the workspace-ready phase fires later via `markSetupComplete` and brings services up cleanly. Component-upgrade flows (post-onboarding) continue to behave as today.
- **`settings:set` workspace-switch path** applies the same `isSetupComplete(newRoot)` gate. Switching into a freshly-created workspace whose framework hasn't been installed (no sentinel) skips `initializeMcpServersWithContextGraph`, `prewarmMcpServers`, indexing-queue start, watcher start, and scheduled-task start — preventing the same pre-gate `uv` race on workspace switch that the createWindow gate prevents on launch. The next app launch (after onboarding completes for that workspace) brings services up via the createWindow path.

**Re-entry semantics:**

- Once the workspace-ready phase has fired in a given process, services stay up for the lifetime of that process. The runtime does not attempt to drop services back to onboarding if `setup_complete` is deleted at runtime.
- Re-evaluation of `isSetupComplete` only happens at the next app launch.

**No migration / no detect-and-write:**

- A workspace without a `setup_complete` sentinel is treated as not-set-up, full stop. The legacy `templates/daily.md` fallback in `checkWorkspaceStatus()` is removed; only the sentinel counts.
- Users with established workspaces predating this gate either re-run onboarding or write the sentinel manually (e.g. `touch .liminis/setup_complete`). Backwards compatibility is explicitly not a goal — keeping the gate trivial and readable was preferred.

**Amendment (2026-04-27): auto-migration carve-out for sentinel-less, framework-installed workspaces (issue #719).**

The "no detect-and-write" stance above proved too strict in practice. Five distinct paths produce indistinguishable on-disk state — framework installed, no sentinel:

1. **Pre-ADR-059 legacy.** Workspace was fully set up before this gate landed.
2. **User quits between framework install and final "Start Using Liminis" click.** The wizard installs the framework as its first step; the sentinel is only written when the user clicks the final button. Quitting in between produces this state.
3. **User clicks "Skip" on the agent stage, then quits before final button.** The skip handler advances to `'complete'`; the sentinel still needs the final click.
4. **`markSetupComplete()` IPC fails silently** at the final-button step. The wizard swallows the error to `console.error` and proceeds. The in-session app works; the next launch finds no sentinel.
5. **App crash mid-wizard.** Same on-disk state as case 2.

The original ADR-059 stance accepted that case 1 users would `touch .liminis/setup_complete` manually. That was a defensible carve-out for legacy workspaces; it was not defensible for cases 2–5, which are ongoing failure modes of the *current* onboarding flow, not historical artifacts. Auto-migrating those cases inside the gate eliminates a class of user-visible breakage without coupling the fix to a separate IPC-retry effort or wizard restructuring.

Migration is implemented in `tryMigrateLegacyWorkspaceSentinel(workspaceRoot)` (`src/main/workspace-init.ts`). It is called from both convergent sentinel-read paths — `checkWorkspaceStatus()` (renderer IPC) and `isSetupComplete()` (main-process workspace-ready gate) — so the migrating launch brings up workspace-bound services correctly. ADR-053's `registry.startAll()` is single-shot per process; if the migration only fired from `checkWorkspaceStatus()`, services would not start until the *next* launch even though the UI would render fine.

**Indicator gate (narrow):** the migration fires only when ALL three indicators are present:

- `.liminis/framework.installed` exists AND its content matches `^version:\s*\S+`. Defeats hand-touched zero-byte files (the install script writes a parseable `version:` line).
- `.liminis/framework-manifest.txt` exists. Written in the same install step as `framework.installed`.
- `.git/` exists at the workspace root. `initializeWorkspace()` always runs `git init` before the framework install.

`config.yaml` and `component-manifest.yaml` were considered and rejected as gate indicators: `config.yaml` is MCP-only (post-framework, optional) and `component-manifest.yaml` is a legacy/upgrade-only path that current onboarding does not write. Including them as required indicators would fail to fire on cases 2–5 and on many case-1 workspaces. Including `control.yaml` would fail to fire on truly ancient pre-rename workspaces (which had `config.yaml` instead). The three indicators above already reject empty / hand-mucked workspaces, which was the original concern.

**Timestamp anchor:** the mtime of `.liminis/framework.installed`, ISO-8601 UTC. Closest honest record of when initialization actually finished. The anchor is approximate (advances on every framework reinstall) but cosmetic only — nothing in the code uses it for control flow, only as a `setupCompletedAt` display value. The migration-mode header in the sentinel file documents the approximation.

**Idempotency:** the migration only runs when the sentinel is absent, and `writeSetupCompleteFile()`'s existing-file branch already preserves any well-formed timestamp. Calling the helper twice in the same launch is a single `existsSync` call.

**Logging:** an `INFO`-level line records the migration with `{ workspaceRoot, anchorTimestamp, indicatorsPresent, migrationCause }`. `migrationCause` is a best-effort heuristic (`legacy-pre-adr-059` if the anchor predates `2026-04-26T00:00:00Z`, else `wizard-incomplete`) — operators can disambiguate from the log line. Cases 1 and 2–5 produce identical on-disk state, so the cause field is informational, not authoritative.

**False-positive risk:** the original ADR rejected detect-and-write because "looks installed" rules are fragile. The narrow gate above (parseable content + manifest + git) is materially stricter than the rejected "any framework artifact" rule. Hand-touching all three indicators to bypass onboarding is possible but explicit — equivalent to the documented `touch .liminis/setup_complete` escape hatch and not in scope for protection.

**Re-onboarding escape hatch:** under the migration logic, deleting only the sentinel and re-launching will silently restore it (the gate still passes). To force re-onboarding on a framework-installed workspace, delete `.liminis/framework.installed` along with the sentinel — that drops the workspace below the gate threshold and routes it back through the welcome flow.

**Out of scope of this amendment:** robust IPC-retry / fallback for `markSetupComplete()`, wizard-flow restructuring (e.g., calling `markSetupComplete()` earlier), and recovery of genuinely partial-onboarding workspaces (where `framework.installed` itself is missing or unparseable). The migration absorbs the user-visible symptom of cases 1–5 regardless of those follow-ups.

**Naming:**

The previous helper `hasSetupComplete()` was renamed to `isSetupComplete()` to match the spec's language and the lifecycle pattern's intent.

**Alternatives considered:**

- **Tear down + restart on runtime sentinel delete.** Rejected: only matters in a corner case the user has not asked for, would require unwinding `registry.startAll`'s single-shot semantics, and would invite races between the watcher and the registry's reverse-topo shutdown. Spec explicitly accepts next-launch-only re-evaluation.
- **Auto-write the sentinel for pre-gate workspaces (detect-and-write heuristic).** Rejected per spec: introduces a fragile "looks installed" rule and locks behavior to whatever framework artifacts happened to ship at the time. Manual `touch .liminis/setup_complete` is the explicit migration path.
- **Register pure in-process wrappers always-on; defer only workspace-touching ones.** Rejected because ADR-053's `registry.startAll()` is single-shot. A partial pre-registration would force either a second `startAll()` invocation later (crash) or a manual partial-start sequence outside the registry. The renderer-side per-query SDK MCP attachments cover the agent's wizard-stage tool surface, so registry-side `mcp:liminis-app` / `mcp:workflow` being deferred has no observable effect.
- **Trust the framework setup skill to call the IPC.** Rejected as brittle: the skill lives in a separate repo (`verveguy/liminis-framework`), and a missing IPC call would silently leave first-run users without services. Wiring `markSetupComplete` into the wizard's "Start Using Liminis" button makes the IPC the canonical trigger.

**Consequences:**

- Onboarding is quiet: no `spawn uv ENOENT`, no context graph crash-loop, no flurry of script-not-found errors during the framework install.
- Renderer's `services:getAll` IPC returns an empty list during onboarding. There is no consumer today; future status-panel UIs must tolerate the empty state pre-gate.
- Per-query agent MCP attachments are checked at every query, not just registration. `claude-agent.ts` covers the gate, but anyone adding a new in-process MCP wrapper to that block needs to think about whether it touches `.claude/skills/`.
- The `setup_complete` sentinel is now load-bearing. Manually deleting `.liminis/setup_complete` will re-route the next launch through the wizard. Worth a one-paragraph mention in the troubleshooting / workspace docs.
- `workspace:initialize` / `workspace:installOnboardingComponents` post-invoke service spawn is silently skipped during onboarding. The workspace-ready phase brings everything up at once when `markSetupComplete` fires; this is invisible to the user but worth knowing during debug.
