# ADR-073: Process-Wide OAuth Metadata Cache and Shared-Budget Retry

**Date:** 2026-07-29
**Status:** Accepted
**Issue:** #932

## Context

Following the discovery-robustness work in #931, every OAuth auth attempt and
every token refresh re-ran the full metadata discovery probe sequence
(`fetchOAuthMetadata`) from scratch — protected-resource metadata, then
authorization-server metadata, potentially across several well-known
candidates. Two problems followed from this:

1. **Redundant round-trips.** Token refresh is the most common path through
   this code (tokens expire routinely), and it only ever needs `token_endpoint`
   — which is static per server. Re-discovering it on every refresh added
   latency and exposed every refresh to a flaky discovery endpoint.
2. **No recovery from a single transient blip.** Krisp's Cloudflare origin
   502s intermittently (`retryable: true, retry_after: 60`). A single 502
   during discovery or Dynamic Client Registration (DCR) failed the entire
   auth attempt with no automatic retry, requiring the user to manually
   re-click "Authorize."

This ADR covers two additions layered on top of #931's discovery pipeline
without changing its tested behavior: an in-memory metadata cache with
single-flight dedup, and a bounded exponential-backoff retry for transient
discovery/DCR failures.

## Decision

### 1. Process-wide, in-memory metadata cache (FR-001, FR-002, FR-003, FR-009)

A new leaf module, `mcp-oauth-metadata-cache.ts`, holds a `Map` from a
normalized server URL (origin + trailing-slash-stripped pathname) to
`{ metadata, expiresAt }`, with a 24-hour TTL
(`OAUTH_METADATA_CACHE_TTL_MS`).

**Deliberately process-wide and cross-workspace, unlike credentials.**
`mcp-config/mcp-oauth.ts` stores OAuth *credentials* (`.liminis/mcp-oauth.json`)
per workspace — those are secrets and must stay workspace-scoped. OAuth
*metadata* (endpoints, `scopes_supported`, `resource`) is non-secret,
immutable-per-server configuration: if the same server URL is configured in
two workspaces, there is no reason to discover it twice. A new contributor
should not assume this cache follows the same workspace-scoping convention as
credentials — it deliberately does not.

**Cache only fully-resolved, successfully-merged results (FR-002).** The
existing `resolve()` control flow in the discovery pipeline has exactly one
partial-result branch: a captured Protected Resource Metadata (PRM) doc whose
`resource` demonstrably belongs to a different server
(`prmMismatchesServer`), falling back to a bare, unmerged AS doc. Every other
non-null result — a full PRM+AS merge, an AS+`authorization_servers` merge, or
a legitimately PRM-less bare-AS server (the "server with no PRM" edge case) —
is a complete, correctly-scoped result and is cache-eligible. This is
expressed as a `cacheEligible: boolean` returned alongside the metadata from
`discoverOAuthMetadata`, computed directly from that existing branch rather
than re-deriving "is this complete" from scratch.

**In-memory only; no persistence across restarts.** Per the spec's
assumptions, a fresh process starts with an empty cache and re-discovers on
first use — acceptable since discovery is otherwise how the app always
behaved, and persisting non-secret, cheaply-rediscoverable metadata to disk
adds no real value.

### 2. `getOAuthMetadata` as the cached entry point; `fetchOAuthMetadata` stays raw

Rather than adding caching inside `fetchOAuthMetadata` itself, the existing
function was refactored into a thin wrapper over a new
`discoverOAuthMetadata(serverUrl, resourceMetadataUrl?, deadline?)` primitive,
and a new exported `getOAuthMetadata(serverUrl, resourceMetadataUrl?,
deadline?)` was added as the cache-check → single-flight → discover →
conditional-cache-write orchestrator.

Production call sites (`performOAuthFlow`, `refreshExpiredOAuthTokens`) call
`getOAuthMetadata`. `fetchOAuthMetadata` remains uncached and single-call
scoped — this is deliberate: the #931 regression suite exercises
`fetchOAuthMetadata` directly, with ~20 tests reusing the same literal server
URL across `it` blocks and asserting on raw `fetch` call counts. Adding
caching to `fetchOAuthMetadata` itself would have made every later test see a
cache hit from an earlier test's successful discovery, silently breaking
those assertions. Keeping the raw primitive separate from the cached
orchestrator keeps "correctness of one discovery call" and "caching across
calls" as independently testable concerns.

### 3. Single-flight discovery keyed by server URL (FR-010)

`withSingleFlight(serverUrl, factory)` in the cache module maintains a
`Map<string, Promise<OAuthMetadata | null>>` of in-flight discovery
operations. Concurrent `getOAuthMetadata` calls for the same normalized server
URL share one discovery operation and its result, rather than each triggering
its own probe sequence — mirroring the `inflightRefreshes` /
`reinitInFlight` single-flight precedent from ADR-067, but keyed by server URL
(process-wide) instead of workspace path.

### 4. Bounded, backoff-aware retry for transient failures (FR-005, FR-006, FR-007, FR-008)

A new `fetchWithTransientRetry` helper in `mcp-oauth.ts` wraps a single `fetch`
call with up to 3 attempts total (1 initial + 2 retries), 200ms base
exponential backoff (200ms, then 400ms), honoring a `Retry-After` response
header when present. Every delay is clamped to the time remaining in the
caller's discovery-budget deadline (`OAUTH_DISCOVERY_BUDGET_MS`, unchanged
from #931), so retries can never turn a bounded discovery call into an
unbounded one.

A failure is transient only for HTTP 429/502/503/504 or a narrow set of
network-level errors (`AbortError`, `TimeoutError`, or Node/undici's actual
fetch-failure shapes — `TypeError: fetch failed`, `ECONNRESET`, etc.). Any
other 4xx, a malformed response body, or an invalid URL is not retried —
discovery fails fast exactly as it did before this issue. This helper is
applied at the three points that make an outbound request during
auth/discovery: the metadata-doc fetch, the AS-metadata fetch, and DCR's POST.

**DCR shares the same budget as metadata discovery, not an independent
timeout.** Before this change, `attemptDynamicClientRegistration` had its own
fixed 15-second timeout (`OAUTH_HTTP_TIMEOUT_MS`), entirely unaware of how
much of the 20-second discovery budget metadata discovery had already
consumed. `performOAuthFlow` now computes one `deadline = Date.now() +
OAUTH_DISCOVERY_BUDGET_MS` up front and threads it through both
`getOAuthMetadata` and DCR, so a slow discovery leaves DCR only the budget
that remains — never a fresh, independent allowance on top.

### 5. Cache invalidation on auth failure (FR-004)

Invalidation reuses the auth-failure signaling chokepoints that already exist
rather than introducing new ones, and invalidates on the existing failure
surface as a whole (not narrowly the FR's literal `invalid_token` /
`invalid_scope` / 401 list) — over-invalidating costs one extra discovery
round-trip; under-invalidating risks wedging a connector for up to the full
24-hour TTL:

- `mcp-http-proxy-server.ts`: a new `signalNeedsAuth()` closure invalidates the
  cache for `serverUrl` and then calls `onNeedsAuth?.(serverName)`, replacing
  all 4 existing bare `onNeedsAuth?.(serverName)` call sites. The
  `reinitErr instanceof HttpAuthError` branch (which returns a `needs-auth`
  error but had no `onNeedsAuth` call) also invalidates directly.
- `mcp-manager.ts`: `validateOAuthServers`'s `HttpAuthError` catch invalidates
  before returning `needs-auth` status.
- `mcp-config/index.ts`: `refreshExpiredOAuthTokens`'s catch block invalidates
  only when the caught error is a new `OAuthTokenError` with `code ===
  'invalid_token'` or `'invalid_scope'` — deliberately narrower here, because
  a refresh can also fail with `invalid_grant` (the refresh token itself is
  dead/revoked) or a network error, neither of which implicates the cached
  metadata. Invalidating on those would defeat caching for reasons unrelated
  to metadata correctness. `OAuthTokenError` (carrying `status` and a parsed
  `code`) replaces the plain `Error` `refreshOAuthToken` previously threw,
  specifically so this call site can make that distinction; `AUTH_ERROR_PATTERN`
  in `mcp-http-proxy-server.ts` was also extended to match `invalid_token` /
  `invalid_scope` literally in `isError` tool results.

## Alternatives Considered

1. **Cache inside `fetchOAuthMetadata` directly.** Rejected — see "single-flight
   discovery" above; would have broken the #931 test suite's cross-test
   isolation without a cache-reset hook wired into ~20 existing tests.
2. **Give DCR its own retry budget independent of discovery.** Rejected —
   directly violates FR-008 ("all retries ... remain within the existing
   `OAUTH_DISCOVERY_BUDGET_MS`"); a slow discovery followed by a fully-fresh
   DCR budget could double the worst-case latency of a single auth attempt.
3. **Invalidate the cache on every refresh failure.** Rejected — a dead
   refresh token (`invalid_grant`) or a transient network blip is unrelated to
   whether the cached endpoints/scopes are still correct; invalidating
   unconditionally would force a full re-discovery on the very next attempt
   for reasons that have nothing to do with metadata staleness.
4. **Persist the cache to disk.** Rejected — out of scope per the spec;
   metadata is cheap to re-derive and the in-memory-only design keeps the
   failure mode simple (a process restart just re-discovers once).

## Consequences

**Positive:**
- A second auth/refresh for an already-discovered server issues zero
  discovery HTTP requests until TTL expiry or invalidation (SC-001).
- A discovery or DCR endpoint that 502s once and recovers no longer requires
  a manual re-click (SC-002).
- A persistently-down discovery endpoint still fails within the existing
  20-second budget and never poisons the cache (SC-003).
- An auth failure against stale cached metadata self-corrects: exactly one
  fresh discovery on the next attempt (SC-004).
- The #931 discovery-correctness suite is unaffected in behavior — only a
  handful of test assertions that counted raw `fetch` calls needed updating to
  account for in-place retries of a persistently-mocked transient failure (the
  discovery *logic* they were written to test is unchanged).

**Negative:**
- Existing `fetchOAuthMetadata` tests that mock a persistent 502 on one
  candidate now take up to ~600ms longer per test (3 attempts × up to 200ms +
  400ms backoff) before falling through to the next candidate, since the
  retry wrapper is applied per-candidate-fetch, not per-discovery-call.
- A server that rotates its OAuth endpoints/scopes without ever producing an
  auth failure the app can observe (e.g. it fails silently in a way that
  doesn't surface as 401/403 or `invalid_token`/`invalid_scope`) would keep
  serving stale cached metadata for up to the 24-hour TTL. This mirrors the
  spec's explicit acceptance of that risk (P2 priority on the self-correction
  story).
