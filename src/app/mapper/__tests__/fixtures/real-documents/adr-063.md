# ADR-063: Auto-Upgrade Gate for Framework Minimum Version

**Date**: 2026-05-29
**Status**: Accepted

## Context

The Liminis app ships with a version of the `liminis-framework` package installed in each workspace's `.venv`. Prior to this ADR, framework upgrades were entirely user-initiated: the user clicked "Upgrade Framework" in the WorkspacePanel UI, which triggered the `UpgradeStateMachine`.

When the framework publishes a breaking cleanup release (e.g., 0.7.0 retiring the Python graph daemon, embedder, and MCP servers), existing workspaces need to upgrade automatically on next app launch. Without an automatic gate:

1. Users on framework < 0.7.0 continue running the app against a version that is no longer tested or supported.
2. Orphaned files in `.venv` (from deleted Python services) persist indefinitely.
3. There is no mechanism to enforce a minimum compatible version.

A related concern: some framework upgrades involve file *deletions* from the package (not just additions or modifications). A standard `uv pip install` upgrade may not remove files that were present in the old version but absent from the new one. For the 0.6.x → 0.7.0 transition, four Python service files (~5,782 lines) and seven heavy dependencies needed to be scrubbed from the `.venv`.

## Decision

### MINIMUM_FRAMEWORK_VERSION constant

A single exported constant `MINIMUM_FRAMEWORK_VERSION` is added to `component-manager/registry-loader.ts`, co-located with the `liminis-framework` registry entry. This is the single source of truth for the minimum required framework version. Bumping this constant is the only change needed to enforce a new minimum.

### Auto-upgrade gate in onWorkspaceRootChanged()

`UpgradeStateMachine.onWorkspaceRootChanged()` is extended to check the installed framework version after crash-recovery initialization completes. If the installed version is below `MINIMUM_FRAMEWORK_VERSION`, the state machine triggers `this.start()` automatically with a log message indicating the auto-upgrade was triggered by the version check, not by user action.

This is **not a silent background upgrade**. The existing upgrade state machine flow ends with a diff dialog that the user must accept. The only behavioral change is that the flow initiates without the user clicking "Upgrade Framework".

### forceReinstall convention for file-deletion upgrades

`installLiminisFramework()` gains a `forceReinstall?: boolean` option. When true, the function injects `FORCE_REINSTALL=1` into the `envOverrides` passed to `addComponentFromScript`, which passes it as an environment variable to the framework's `install.sh` script.

The `forceReinstall` flag is set to `true` when the upgrade is transitioning from a version below `'0.7.0'` (the specific release that deleted Python files). For other transitions (e.g., 0.7.0 → 0.7.1), the standard install flow runs.

The `install.sh` script in the framework repo must honor this env var:

```bash
if [ "$FORCE_REINSTALL" = "1" ]; then
  uv sync --reinstall
else
  uv sync
fi
```

If `install.sh` does not implement this check, the `FORCE_REINSTALL` env var is silently ignored and a normal install runs (safe degradation).

## Alternatives Considered

**Option B: Gate in index.ts createWindow()** — A new version check between workspace confirmation and the workspace-ready phase. Rejected: more complex, requires new IPC plumbing, and less cohesive than placing the check inside the existing upgrade state machine.

**Positional arg `--force-reinstall` to install.sh** — Pass the flag as a positional script argument. Rejected: `addComponentFromScript` already supports `envOverrides`; positional arguments conflict with the existing `$1` version string parsing in `install.sh`.

**Sentinel file to detect post-cleanup install** — Add a `.liminis/framework-0.7.0-clean.marker` file after a successful force-reinstall to avoid re-running it on subsequent opens. Rejected as over-engineering: the version check already guards this path (once upgraded to 0.7.0, `isVersionBelow(version, MINIMUM_FRAMEWORK_VERSION)` returns false and the auto-upgrade does not trigger).

## Consequences

**Positive**:
- Existing workspaces auto-upgrade to the minimum supported version without user action.
- The 0.6.x → 0.7.0 transition scrubs orphaned Python service files from `.venv`.
- `MINIMUM_FRAMEWORK_VERSION` is a single constant that governs all version checks; no duplication.
- `forceReinstall` is a named option in `installLiminisFramework()`; future callers can use it for other file-deletion upgrades.

**Negative / Trade-offs**:
- Users see an unexpected diff dialog on workspace open (the first time they open a workspace with an outdated framework). The dialog is clear and user-mediated; it is not silent.
- The `forceReinstall` path depends on the framework's `install.sh` implementing `FORCE_REINSTALL=1` handling. App-side and framework-side changes must be coordinated.
- First upgrade after this change may be slower than usual (uv re-downloads cached packages). This is a one-time cost per workspace.

## Implementation

- `liminis-app/src/main/component-manager/registry-loader.ts`: `MINIMUM_FRAMEWORK_VERSION = '0.7.0'`
- `liminis-app/src/main/component-manager/index.ts`: `isVersionBelow()`, `MINIMUM_FRAMEWORK_VERSION` re-export, `installLiminisFramework({ forceReinstall })`
- `liminis-app/src/main/upgrade-state-machine.ts`: auto-upgrade check in `onWorkspaceRootChanged()`
- See also: issue #837, companion `liminis-framework` issue #190 (which implements the `FORCE_REINSTALL` env var in `install.sh`).
