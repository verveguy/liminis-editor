# ADR-061: First-Launch Local-Inference Model Setup

**Date:** 2026-05-24
**Status:** Accepted
**Issue:** #794

## Context

The Swift `local-inference` sidecar serves `/v1/embeddings` from a CoreML
BGE-base-en-v1.5 model. Prior to this change, two prerequisites had to be in
place before the sidecar would start:

1. A `.mlpackage` or `.mlmodelc` for the model (produced by
   `convert-embedding-model.py`).
2. A HuggingFace tokenizer cache laid out at
   `<hubCache>/models/BAAI/bge-base-en-v1.5/` (populated as a side effect of
   `verify-tokenizer-parity.py`).

`startLocalInference()` set no model-related env vars, so the sidecar fell back
to a relative-path default and exited with a missing-file error on a clean
install. Production users had no way to make this work without running Python
scripts by hand, and the framework's embedder cutover
(`verveguy/liminis-framework#179`) was blocked on this.

`MLModel.compileModel(at:)` produces a device-tailored `.mlmodelc` and only
works from Swift — the compile step cannot run in Electron's main process. The
compile costs 5–15 s on Apple Silicon and only needs to happen once per device.

## Decision

Bundle the `.mlpackage` and tokenizer files inside the `.app`, and on first
launch compile the model once into a per-device cache so subsequent launches
load in < 500 ms (REQ-02 / SC-003).

The work is split across three layers:

1. **Build pipeline** (`liminis-app/package.json`, `extraFiles`): the
   `.mlpackage` directory and the five required tokenizer files are bundled
   under `Resources/models/...` inside the `.app`. The staged tokenizer
   directory includes `config.json` (BERT model config) alongside the four
   core tokenizer files, plus a `.cache/huggingface/download/` subtree
   containing one `.metadata` marker per staged file — required by the
   swift-transformers offline loader contract (see `prepare-tokenizer.py`
   docstring for the full contract). A `check-embedding-assets` pre-step
   gates `pnpm package` with a clear error when assets are missing.
   The umbrella `pnpm prepare-embedding-assets` script runs both
   `convert-embedding-model.py` and `prepare-tokenizer.py`.

2. **Electron main process** (`local-inference-lifecycle.ts`): resolves the
   bundled paths (packaged vs dev), idempotently copies tokenizer files into
   the per-device cache, and threads three env vars into the spawned sidecar:
   `LOCAL_INFERENCE_EMBEDDING_MODEL` (path to bundled `.mlpackage`),
   `LOCAL_INFERENCE_MLMODELC_CACHE` (per-user cache dir), and
   `LOCAL_INFERENCE_HF_CACHE` (per-user tokenizer cache dir).

3. **Swift sidecar** (`SetupCache.swift`, `EmbeddingsHandler.swift`): on every
   start checks `<cache>/compiled.ok`; if present and the build hash matches,
   loads the cached `.mlmodelc` directly. Otherwise cleans any stale cache,
   compiles to a temp dir, atomically renames into the cache via
   `bge-base-en-v1.5.mlmodelc.tmp/` → `bge-base-en-v1.5.mlmodelc/`,
   sanity-loads the result, and writes the sentinel via `O_CREAT|O_EXCL|O_WRONLY`
   with the source weights' SHA-256 as the body.

### Sentinel atomicity and cache invalidation

- `compiled.ok` is written **after** the directory rename and a sanity-check
  `MLModel(contentsOf:)` load both succeed.
- The sentinel body is the SHA-256 of `Data/com.apple.CoreML/weights/weight.bin`
  inside the source `.mlpackage`. On a future model upgrade, the bundled
  weight hash will diverge from the cached sentinel and the cache will
  automatically re-compile.
- If the sentinel is absent at startup (mid-compile crash), the sidecar runs
  `cleanStaleCache` to remove any `*.mlmodelc*` directories before retrying.

### Dedicated IPC channel for setup progress

Local-inference setup runs **before** the context graph `serviceProgress` chain
attaches (context graph depends on `local-inference` per the service registry),
so its progress cannot ride the context graph's `workspace:serviceProgress` channel
without missing the early events. A separate
`workspace:localInferenceProgress` channel is used instead:

- The sidecar emits `[setup] <stage>[ <message>]` lines on stderr for stages
  `compiling_model`, `installing_model`, `verifying_model`, `model_ready`,
  `setup_failed`. (The Electron-side tokenizer copy is fast enough that no
  `copying_model` event is emitted; the parser still accepts the stage so a
  future Electron-side emit can light up without renderer changes.)
- `local-inference-lifecycle.ts` parses these lines and forwards typed events
  to an injected sink. The default sink in `main/index.ts` forwards to the
  mainWindow.
- `SetupWizard.tsx` subscribes via `window.api.workspace.onLocalInferenceProgress`
  unconditionally on mount (not gated on a later stage as `onServiceProgress`
  is), so compile-step progress is shown immediately on first launch.

## Alternatives Considered

1. **Bundle a pre-compiled `.mlmodelc` instead of the `.mlpackage`**
   Rejected: would force CI to run `coremltools` or check in a large binary.
   The 5–15 s compile is one-time per device and fits naturally into the
   onboarding progress channel.

2. **Compile in Electron main process**
   Rejected: `MLModel.compileModel(at:)` is Swift-only; there is no Node-side
   CoreML binding.

3. **A `--compile-only <output>` sidecar mode** (two spawns)
   Rejected: doubles process management cost without reducing coupling; the
   sidecar already owns all CoreML knowledge.

4. **Unify with the context graph's `workspace:serviceProgress` channel**
   Rejected: the listener attaches inside `initializeMcpServersWithContextGraph`,
   which runs **after** `startLocalInference()` returns, so compile-step
   events would be missed by the renderer.

5. **Download the model on first launch instead of bundling**
   Rejected: introduces a real failure mode in onboarding (mid-download
   interrupt), and ~90 MB is small relative to the app's existing footprint
   (Electron + Python framework + LadybugDB). PR #529 set the precedent of
   bundling companion artifacts.

## Consequences

**Positive:**
- First launch on a fresh install reaches "embedder ready" without any
  user-facing Python step.
- Warm-cache startup is < 500 ms (per SC-003), unblocking the framework F1
  embedder cutover (`verveguy/liminis-framework#179`).
- Model upgrades are automatic — a new bundled `.mlpackage` invalidates the
  cache via the build-hash sentinel mismatch.
- Crash safety: a half-written `.mlmodelc` cannot be mistaken for a complete
  one — the sentinel write is the linearization point.

**Negative:**
- DMG size grows by ~90 MB.
- Notarization processes ~90 MB of small files inside the `.mlpackage`,
  which may slow CI submission.
- ~~Contributors must run `pnpm prepare-embedding-assets` before `pnpm package`.~~
  Embedding assets are now fetched automatically by `pnpm bootstrap` and
  `pnpm package` from the GitHub Release artifact store — no `uv` or Python
  required on the default path. See [ADR-066](./adr-066.md) for the distribution
  architecture. Local regeneration via `pnpm bootstrap --refresh-assets` remains
  available for contributors bumping the model revision.

**Out of scope (deferred):**
- Dynamic batch dimension on the `.mlpackage`.
- Intel / x86_64 support (the app is arm64-only).
- Runtime model swap UI.

**Update (2026-05-24, issue #810):**
After the bundled model loads, the sidecar now validates its `last_hidden_state`
output description (presence, dtype, shape) against a single
`supportedOutputDataTypes` set on `CoreMLEmbeddingActor` and the expected
`[1, 512, 768]` shape. Mismatches throw distinct, named errors
(`embeddingOutputMissing`, `embeddingOutputDtypeUnsupported`,
`embeddingOutputShapeMismatch`) that propagate through the existing `[setup]
setup_failed` channel into the SetupWizard with a specific message naming the
observed and expected values. The per-request misleading `embeddingModelNotLoaded`
error for schema mismatches (introduced by PR #805) is gone. The handler also
accepts `float16` outputs in addition to `float32`, so the production
`convert-embedding-model.py` (which sets `compute_precision=FLOAT16`) works
end-to-end without a sidecar code change.

**Update (2026-05-25, issue #811):**
The sidecar integration test fixtures are now governed by a script-hash divergence
guard. See [ADR-062](./adr-062.md) for the strategy. In summary: every fixture
generator script (`prepare-tokenizer.py`, `convert-embedding-model.py`, and the two
stub generators) has a corresponding `.script-hash` sentinel committed to
`Tests/LocalInferenceTests/Fixtures/`. `check-fixture-freshness.sh` (and a dedicated
CI job) verify the hashes match on every PR. `refresh-test-fixtures.sh` provides a
single command to regenerate all fixtures and update all sentinels. Both production
scripts now accept a `--revision` flag (defaulting to `PINNED_BGE_REVISION`) to pin
the HuggingFace model revision for reproducible fixture regeneration.
