# ADR-067: MCP HTTP Proxy Session Management and Active-Proxy Registry

**Date:** 2026-06-22
**Status:** Accepted
**Issue:** #882

## Context

MCP HTTP Streamable servers assign a `Mcp-Session-Id` per connection (spec §6.2.1).
Sessions expire server-side — the server discards state and returns an error on the
next tool call. Prior to this ADR, the in-process proxy (`createHttpProxyMcpServer`)
had no recovery path: a stale session caused every subsequent tool call to fail with
a JSON-RPC error until the user restarted the agent run.

A second, related problem: the settings panel polls `validateOAuthServers` on every
`getMcpServerStatus` call (roughly once per minute). Each poll called
`createHttpProxyMcpServer`, which performs a full `initialize` / `tools/list`
handshake. For OAuth servers with rotating refresh tokens (e.g. Slack) this creates
two concurrent refresh flows when a panel poll races an in-flight agent call,
invalidating the token the agent just obtained.

## Decision

### 1. Session recovery with single-flight re-init (FR-001, FR-005, FR-006, FR-007)

Inside the `createHttpProxyMcpServer` closure, a mutable `currentSessionId` tracks
the live session. Every tool call goes through `callWithSessionRecovery`:

1. Attempt the tool call with `currentSessionId` in the `Mcp-Session-Id` header.
2. On any error (JSON-RPC or HTTP), call `reinitSession()` to re-establish a fresh
   session, then retry the tool call exactly once with fresh auth headers.
3. If re-init itself fails with `HttpAuthError` (401/403), surface `needs-auth` so
   the UI can prompt re-authorization without a cryptic error message.
4. If the server returns a new `Mcp-Session-Id` header mid-call (session rotation,
   FR-002), adopt it immediately so subsequent calls use the rotated ID.

`reinitSession()` is single-flight: a shared `reinitInFlight: Promise<void> | null`
ensures that concurrent tool calls that hit a dead session all await the same
re-init rather than each launching their own, which would exhaust server session
quotas and amplify auth traffic.

### 2. Active-proxy registry for panel-polling fast path (FR-003, FR-004)

A module-level `Map<string, number> activeProxies` ref-counts live proxy instances
per server name. `createHttpProxyMcpServer` increments the count only after all
async setup (auth headers, tool discovery) has succeeded, and returns a `dispose()`
function (called in the agent-run `finally` block) that decrements it, deleting
the entry only when the count reaches zero.

Using a ref-count rather than a `Set<string>` handles concurrent agent runs: if
two sessions each create a proxy for the same server, the first `dispose()` call
decrements to 1 (not 0), so `isProxyActive` stays `true` and the panel fast-path
continues to suppress network probes until the last proxy is released.

Registering after success means a factory that throws during discovery (auth error,
network failure) never pollutes the registry — the caller has no `dispose()` to
call, so the count must not be incremented.

`validateOAuthServers` in `McpManager` checks `isProxyActive(name)` first:

- **Active proxy (fast path):** return `connected` immediately — no network call.
  The proxy's own session-recovery loop keeps the session alive; the panel has
  nothing to verify.
- **No active proxy (slow path):** call `probeOAuthServer`, which performs a
  lightweight `discoverTools` handshake to confirm the server is reachable.

This eliminates the token-refresh race: while an agent run is active, panel polls
are no-ops for all OAuth servers that proxy is connected to.

### 3. Token-refresh dedup (FR-004)

`refreshExpiredOAuthTokens` wraps its body in a per-`workspacePath` in-flight
guard using a shared `inflightRefreshes: Map<string, Promise<void>>` from a
dedicated `mcp-refresh-dedup.ts` module. A concurrent caller awaits the existing
promise and returns an empty array rather than starting a second refresh. This
prevents double-refresh even when the panel slow path and proxy auth code race on
the same workspace.

The dedup map lives in its own module to avoid circular imports between
`mcp-http-proxy-server.ts` and `mcp-config/index.ts`.

## Disposal Contract

`createHttpProxyMcpServer` now returns `{ server: SdkMcpServerConfig, dispose: () => void }`.
The caller (`claude-agent.ts`) stores all disposers in `oauthProxyDisposers[]` and
calls each in the `finally` block of the agent run. If `dispose()` is not called
(e.g. process crash), `activeProxies` retains the stale entry until the next
process start (module is re-loaded). This is acceptable: a fresh process starts with
an empty registry, and the first panel poll falls through to `probeOAuthServer`.

## Unclosed Probe Session Limitation

`probeOAuthServer` calls `discoverTools` to establish a test connection but does
not send an HTTP `DELETE` to close the resulting server session (MCP Streamable
HTTP spec §6.2.4). Servers that track sessions will accumulate one dangling probe
session per panel poll interval. This is tracked as a known limitation — a
`// TODO(#882)` comment marks the code site. Closing probe sessions requires
parsing the `Mcp-Session-Id` returned from the `initialize` response and issuing a
DELETE, which adds complexity. The dangling session is harmless for all known MCP
servers (sessions expire on inactivity) but may surface as a warning in server logs.

## Alternatives Considered

1. **Re-run `createHttpProxyMcpServer` on each panel poll**: Rejected — causes the
   rotating-token race described above. Full init handshakes are expensive and leak
   sessions.
2. **Keep local per-proxy `inflightRefreshes` rather than a shared module**: Rejected
   — if `getAuthHeaders` inside the proxy and `refreshExpiredOAuthTokens` inside
   the panel path both manage their own maps, they key on the same `workspacePath`
   but use different map instances, so two concurrent refreshes still race.
3. **Merge dedup into `getAuthHeaders` directly**: Rejected — `getAuthHeaders` is
   called once per tool call and per-server, not per-workspace; the dedup granularity
   must be the workspace path (shared across all servers) to prevent racing when
   multiple servers in the same workspace expire at the same time.

## Consequences

**Positive:**
- Stale MCP sessions self-heal without user intervention (SC-001).
- Panel polling never races the agent's token refresh (SC-002, SC-003).
- A single `initialize` call regardless of how many concurrent tool calls hit a
  dead session simultaneously (SC-004).
- `dispose()` pattern integrates cleanly with the existing agent-run `finally` block.

**Negative:**
- `createHttpProxyMcpServer` callers must destructure `{ server, dispose }` and
  call `dispose()` — forgetting `dispose()` leaks the registry entry for the
  process lifetime.
- Probe sessions are not closed (known limitation above).

## Addendum: Re-authentication support (issue #884, 2026-06-22)

### `clearActiveProxy` — force-clear for re-auth flow

`clearActiveProxy(serverName: string): void` forcibly removes the `activeProxies` entry for a server without decrementing the ref-count. It is called exclusively by `McpManager.reAuthenticateMcpServer` after a successful full OAuth re-consent, so that subsequent `getMcpServerStatus` calls fall through to the slow-path probe with the new token rather than returning the cached `connected` fast-path.

Disposal safety: any existing `dispose()` closures held by in-flight agent runs will fire after the force-clear. `dispose()` computes `(activeProxies.get(serverName) ?? 1) - 1`, yielding `0` (key absent → default 1, minus 1), and then calls `activeProxies.delete(serverName)` on an already-absent key — a safe no-op. If a new proxy for the same server is created between the force-clear and a subsequent `dispose()`, the new proxy starts a fresh ref-count from `1`; the old `dispose()` call will drive it to `0` and delete the key, but the new proxy's own `dispose()` will fire the same path without crashing. This transient undercount is acceptable for the narrow re-auth window.

### `onNeedsAuth` callback — `isError` auth detection in `callWithSessionRecovery`

`createHttpProxyMcpServer` accepts an optional 6th argument `onNeedsAuth?: (serverName: string) => void`. Inside `callWithSessionRecovery`, after `sendToolCall` returns a result, the result is inspected for auth-shaped failure: `isError: true` and content matching the pattern `invalid_auth_token|invalid_auth|not_authed|token_revoked|account_inactive|unauthorized`. This covers the third error channel — HTTP 200 responses where the MCP server embeds auth errors in the JSON-RPC result body rather than returning 401/403.

When detected, one reinit+retry cycle runs (mirroring the thrown-error path). If the retry also returns an auth-shaped `isError` result, `onNeedsAuth?.(serverName)` is called and the result is returned as-is. No loop beyond one retry. In `claude-agent.ts`, the callback delegates to `McpManager.notifyNeedsAuth(serverName)`, which fires `agent:mcp-needs-auth { serverName }` via `sendToRenderer`. `McpPanel.tsx` subscribes via `window.api.agent.onMcpNeedsAuth` and flips the local server status to `'needs-auth'`, surfacing the Re-authenticate button for immediate user action.
