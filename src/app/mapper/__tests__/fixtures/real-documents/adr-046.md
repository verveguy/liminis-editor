# ADR-046: Documentation Structure — Public vs Internal (2026-03-17, amended 2026-04-22)

**Context:**
- Liminis has accumulated documentation in multiple locations without clear audience distinction
- `docs/project_notes/` contains internal developer records (ADRs, key_facts.md, bugs.md)
- `docs/*.md` contains technical architecture documents
- User-facing documentation was originally written under `docs/features/` alongside internal docs
- GitHub Pages serves the marketing + user-facing site from `marketing-site/docs/` via VitePress
- `liminis-viewer/` is sometimes mistaken for a documentation site — it's actually an experimental notebook renderer for the companion web app
- Future developers need clarity on where to put new documentation

**Decision:**

Establish a two-category documentation structure:

**1. Public Documentation (`marketing-site/docs/guide/`) — User-Facing**
- Audience: End users of Liminis
- Purpose: Feature guides, setup instructions, usage examples
- Format: VitePress-flavored markdown; served from `marketing-site/docs/` via the `deploy-marketing.yml` workflow under the `/liminis/guide/…` URL prefix
- Tone: How-to focused, assumes no codebase knowledge
- Structure: `guide/index.md` is the landing; sidebar groups are configured in `marketing-site/docs/.vitepress/config.ts`

| Document | Purpose |
|----------|---------|
| `guide/search-guide.md` | Unified search (⌘K) and the knowledge-graph explorer |
| `guide/web-clipper.md` | MarkDownload browser extension setup |
| `guide/remote-access.md` | Mobile app connectivity |
| `guide/discussions.md` | Community discussions feature |
| `guide/workflow.md` | Kanban / workflow visualization |
| `guide/actions.md` | Todo/checkbox management |
| `guide/file-ingestion.md` | File import and indexing |
| `guide/mcp-architecture.md` | MCP tool ecosystem and user extensibility (Advanced) |

**2. Internal Documentation (`docs/project_notes/`, `docs/*.md`) — Developer-Facing**
- Audience: Contributors and maintainers
- Purpose: Architectural decisions, project configuration, technical deep-dives
- Format: Markdown with code examples, API references, implementation details
- Tone: Technical, assumes familiarity with codebase

| Location | Contents |
|----------|----------|
| `docs/project_notes/decisions/` | ADRs (architectural decisions) |
| `docs/project_notes/key_facts.md` | Ports, credentials, IPC handlers, service accounts |
| `docs/project_notes/bugs.md` | Supplementary bug solution notes |
| `docs/*.md` | Internal architecture, testing strategy, callback architecture, onboarding fix logs, SDK integration notes, model-persistence notes, etc. |

**Clarification: liminis-viewer is NOT a Documentation Site**

The `liminis-viewer/` directory contains an experimental notebook renderer for the companion web application. It is:
- A React/Vite application for rendering notebook content
- NOT related to product documentation
- NOT a documentation hosting solution

Do not confuse liminis-viewer with documentation infrastructure.

**Migration Guidelines:**

When adding new documentation:
1. Ask: "Is this for end users or developers?"
2. User-facing → `marketing-site/docs/guide/{feature}.md`, wire a sidebar entry in `marketing-site/docs/.vitepress/config.ts`
3. Developer-facing architectural decision → `docs/project_notes/decisions/adr-{N}.md`
4. Developer-facing technical reference → `docs/{topic}.md` or `docs/project_notes/key_facts.md`
5. Update the appropriate index file (sidebar config for guide pages; `decisions/index.md` for ADRs)

When moving existing documentation:
1. If currently user-facing but in wrong location → move to `marketing-site/docs/guide/`
2. Rewrite for target audience (remove implementation details for users, add them for developers)
3. Update any cross-references — internal docs referencing the old `docs/features/` path should point to `marketing-site/docs/guide/…` (source path) or the `/liminis/guide/…` published URL, whichever is clearer

**Alternatives Considered:**
- Single `docs/` directory with audience prefixes → Rejected: file naming becomes awkward (`user-search.md` vs `dev-search.md`)
- Separate repository for user docs → Rejected: unnecessarily complex, harder to keep in sync
- Wiki for user docs → Rejected: GitHub Pages from repo is simpler and version-controlled
- Publishing `docs/features/` directly as GitHub Pages → Rejected in #670: the marketing site already runs VitePress on the same Pages deploy, so consolidating user-facing docs into one VitePress instance avoids a second build pipeline

**Consequences:**
- New contributors can quickly identify where documentation belongs
- The VitePress marketing site serves both marketing copy and the user guide without a tooling split
- Internal documentation remains colocated with code (single source of truth for engineering context)
- liminis-viewer confusion is explicitly addressed
- The original `docs/features/` directory has been retired (issue #670) — user-facing docs now live exclusively under `marketing-site/docs/guide/`
