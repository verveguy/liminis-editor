# ADR-040: Graphiti Edge Direction — Undirected Query Workaround (2026-02-27)

**Context:**
- Graphiti stores directed relationships in Neo4j as `(source:Entity)-[e:RELATES_TO]->(target:Entity)`
- The Graphiti SDK's `EntityEdge.get_by_node_uuid()` method uses an **undirected** Cypher pattern: `(n)-[e:RELATES_TO]-(m)` — note the missing `>` arrow
- This means `source_node_uuid` and `target_node_uuid` on the returned edge objects can be swapped relative to what's stored in Neo4j
- Investigation confirmed this method has **zero internal callers** within graphiti_core — it's a public API convenience method that was never used by the library's own LLM pipelines (which only consume fact text, not direction)
- For the knowledge graph visualizer (ADR-039), correct edge direction is essential: arrowheads point the wrong way, fact card headers show `Source [REL] Target` reversed, and the semantic meaning of directed relationships (e.g., "Alice MANAGES Bob" vs "Bob MANAGES Alice") is lost

**Decision:**
Work around the undirected query by using a **two-query approach** in `_handle_get_entity_neighbors` (server.py):

1. Call `EntityEdge.get_by_node_uuid()` to **discover** which edges connect to the entity (undirected, but gives us the UUIDs)
2. Slice to `num_results` in Python (the method doesn't accept a `limit` parameter)
3. Call `EntityEdge.get_by_uuids()` to **re-fetch** the same edges via a **directed** Cypher query that preserves true `source_node_uuid`/`target_node_uuid`

```python
# Discovery (undirected — may swap source/target)
undirected_edges = await EntityEdge.get_by_node_uuid(graphiti.driver, entity_uuid)
edge_uuids = [e.uuid for e in undirected_edges[:num_results]]

# Re-fetch with correct direction
edges = await EntityEdge.get_by_uuids(graphiti.driver, edge_uuids) if edge_uuids else []
```

**Why not fix graphiti_core directly?**
- We use graphiti_core as a pip dependency; forking it adds maintenance burden
- The fix is trivial (add `>` to the Cypher pattern) but needs upstream acceptance
- The two-query workaround is isolated to our server.py and can be removed if/when upstream fixes it
- Performance cost is minimal: one extra query per `getNeighbors` call, and `get_by_uuids` is efficient (batch UUID lookup)

**Additional finding — `get_by_node_uuid` has no `limit` parameter:**
Unlike `get_by_group_ids` which accepts `limit`, `get_by_node_uuid` fetches all edges and returns them. We slice in Python (`[:num_results]`). For highly-connected entities this could be inefficient, but is acceptable for typical knowledge graph sizes.

**Consequences:**
- ✅ Edge direction is now correct for all visualization consumers
- ✅ No fork of graphiti_core required
- ✅ Workaround is isolated and documented (easy to remove later)
- ✅ Arrowheads, fact card headers, and relationship panels all show correct direction
- ❌ Extra database round-trip per `getNeighbors` call
- ❌ No server-side limit on initial discovery query (Python-side slice)
- ❌ Workaround needed until graphiti_core fixes the upstream issue
