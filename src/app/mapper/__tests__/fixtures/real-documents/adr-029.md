# ADR-029: Beads Work Tracker Architecture - Build vs. Integrate (2026-02-04)

> **Superseded (2026-03-30):** The `bd` CLI + Dolt backend described in this ADR has been replaced by a pure-TypeScript JSONL-based work item tracker (see issue #564). The conceptual model (work items, dependencies, status workflow) remains the same, but the implementation no longer requires any external binaries or database servers. Data is stored in `.beads/items.jsonl` and `.beads/interactions.jsonl` — zero-install, git-friendly, and always available.

**Context:**
- Need cross-session work item tracking for "constant gardener" style agent activities
- Activities include: knowledge graph updates, transcription correction, strategy document updates, action item cleanup
- Agents or code create work items ("beads") that are picked up by future agent sessions
- An initial plan (`.cursor/plans/beads-architecture.plan.md`) proposed building a custom system from scratch
- Steve Yegge's [Beads](https://github.com/steveyegge/beads) project (12.8k stars) provides a mature, git-backed issue tracker designed for AI agents
- Beads has its own [MCP server](https://steveyegge.github.io/beads/integrations/mcp-server) (`beads-mcp`) exposing ~15 tools

**Original Decision (now superseded):**
- **Integrate the real `bd` CLI + `beads-mcp`** as the foundation layer rather than building from scratch
- Configure `beads-mcp` as an external stdio MCP server via the Liminis MCP fragment system
- Agents interact with beads via standard MCP tools: `beads_create`, `beads_list`, `beads_ready`, `beads_update`, `beads_close`, `beads_add_dependency`, etc.
- Build a thin Liminis adapter layer on top for Liminis-specific features (Phase 2):
  - Groomer/consolidation logic (merging redundant work items)
  - Circuit breaker (rate limiting, token budgeting)
  - Smart bundling (grouping related beads for efficient agent consumption)
  - Seance (context restoration from bead lineage)
- Chat-bead association: bidirectional linking between chat sessions and beads
  - Chat metadata stores the bead ID that triggered it
  - Bead logs reference which chat session worked on it
- Auto-approve bead MCP tools (local JSON operations, no security risk)

**Current Implementation (2026-03-30):**
- Pure-TypeScript JSONL module (`work-items.ts`) replaces all `bd` CLI and Dolt dependencies
- Work items stored in `.beads/items.jsonl` (one JSON object per line)
- Interactions/comments stored in `.beads/interactions.jsonl` (append-only log)
- In-process workflow MCP server exposes 12 `work_*` tools — always available, no binary checks
- No external dependencies, no installation step, no database server
- Same conceptual model: status workflow, dependency tracking, type system, priority levels

**Rationale for Change:**
- `bd` CLI required Go binary installation + Dolt server on port 3307
- Installation fragility: `bd init` silently fails if dolt isn't in PATH (#563)
- Operational overhead (server process, lock files, migrations) was overkill for our needs
- JSONL provides sufficient performance for typical project sizes (< 1000 items)

**Alternatives Considered:**
- Build custom system from scratch (original plan) → Rejected: duplicates mature, battle-tested functionality; Beads already handles git-backed persistence, dependency tracking, hash-based IDs, compaction/memory decay
- Use only `beads-mcp` without future custom layer → Rejected: need Liminis-specific business logic (consolidation, circuit breaker, seance)
- Use JSONL files directly without `bd` → Originally rejected for performance concerns, but **adopted in 2026-03 after operational pain with `bd`/Dolt outweighed the benefits**

**Consequences:**
- ✅ Zero-install: no external binaries, no database server, no port allocation
- ✅ Always available: workflow MCP server starts unconditionally
- ✅ Git-friendly: JSONL files are line-oriented and human-readable
- ✅ Same MCP tool interface: all 12 `work_*` tools preserved
- ✅ Simpler codebase: single `work-items.ts` module replaces two CLI wrappers
- ❌ No built-in compaction/memory decay (can be added later if needed)
- ❌ Full-file read/write for updates (acceptable at < 1000 items)
