# ADR-034: Claude Code Configuration Strategy (.claude/ Directory) (2026-02-13)

**Context:**
- The liminis project ecosystem spans multiple repos (liminis, liminis-framework, kiln, remarkable) each with their own `.claude/` configurations
- The liminis-framework repo has well-established conventions for skills and agents, documented in `docs/AGENT-SKILLS-GUIDE.md`, `docs/AGENT-SKILLS-QUICK-REF.md`, `docs/CONFIG-DIRECTORY-PATTERN.md`, and `docs/TEMPLATE-IN-SKILL-PATTERN.md`
- These existing conventions define a three-layer architecture: Framework (`.claude/`) → Configuration (`config/`) → Content (workspace directories)
- However, two gaps exist in the current approach:
  1. **`AGENTS.md` is NOT auto-discovered by Claude Code** — only `CLAUDE.md` is auto-loaded. The framework's 260-line `AGENTS.md` requires explicit reading.
  2. **`rules/` is not used anywhere** — Claude Code supports `.claude/rules/*.md` with path-scoped auto-loading, which would reduce prompt overhead by loading guidance only when relevant files are being edited
- The liminis app repo has a monolithic `CLAUDE.md` (184 lines) mixing universal conventions with path-specific Electron/ADR guidance
- Accumulated permission cruft in `settings.local.json` files (legacy syntax, one-off commands)

**Decision:**

Extend the existing `.claude/` conventions (skills, agents, settings) with two additions — `CLAUDE.md` as the auto-loaded entry point and `rules/` for path-scoped guidance — while preserving the framework's established patterns.

**Claude Code Auto-Discovery (what actually gets loaded):**

| File | Auto-loaded? | When |
|------|-------------|------|
| `CLAUDE.md` | Yes | Always (walks up directory tree) |
| `.claude/rules/*.md` | Yes | When working on files matching `paths:` frontmatter |
| `.claude/agents/*.md` | Yes | Available for Task tool delegation |
| `.claude/skills/*/SKILL.md` | On invocation | When user triggers slash command |
| `AGENTS.md` | **No** | Must be explicitly read |
| `.claude/settings.json` | Yes | Always (permissions) |

**1. `CLAUDE.md` — Always-active project instructions (NEW for framework, existing for liminis app)**
- Every repo MUST have a `CLAUDE.md` — this replaces `AGENTS.md` as the entry point
- Keep concise: target <120 lines
- Contains universally-applicable content: role definition, package manager preferences, git workflow, skill/agent index
- References ADRs by number, does not duplicate their code examples
- For the framework: `AGENTS.md` → `CLAUDE.md` (rename, then slim down)

**2. `.claude/rules/` — Path-scoped modular rules (NEW)**
- Use YAML frontmatter `paths:` to scope rules to relevant file patterns
- One rule file per concern (e.g., `typescript.md`, `electron-renderer.md`, `daily-notes.md`)
- Rules without `paths:` frontmatter are always-active (use sparingly — prefer CLAUDE.md for that)
- This is where code examples, anti-patterns, and detailed guidance live (keeps CLAUDE.md slim)
- Name files descriptively: `{domain}.md` or `{domain}-{scope}.md`

**3. `.claude/agents/` — Subagent definitions (EXISTING, no changes)**
- Conventions already well-documented in `AGENT-SKILLS-GUIDE.md` and `AGENT-SKILLS-QUICK-REF.md`
- One `.md` file per agent with YAML frontmatter (`name`, `description`, `model`) and markdown system prompt
- Agent files define: role, skills to reference, delegation triggers, quality standards

**4. `.claude/skills/` — Slash-command workflows (EXISTING, no changes)**
- Conventions already well-documented in `AGENT-SKILLS-GUIDE.md` and the `create-skill` skill
- Each skill in its own directory: `.claude/skills/{name}/SKILL.md`
- Optional: `scripts/`, `pyproject.toml`, `references/`, `*.template.md` within skill directory
- Skills are for interactive workflows triggered by user (not passive guidance — that's `rules/`)
- Keep SKILL.md under 500 lines; use progressive disclosure with sibling files

**5. `settings.json` / `settings.local.json` — Permissions (EXISTING, needs cleanup)**
- `settings.json`: Shared, committed permissions (for shipped configurations like liminis-framework)
- `settings.local.json`: Personal, gitignored permissions
- Use modern space syntax: `Bash(git *)` not `Bash(git:*)`
- Never allow broad destructive permissions in shared `settings.json` (scope narrowly: `Bash(rm ingestion/*)` not `Bash(rm *)`)
- Remove permissions that duplicate built-in tools (no `Bash(cat *)`, `Bash(grep *)`, `Bash(find *)` — use Read, Grep, Glob)
- Periodically audit for accumulated one-off permissions (auto-saved by Claude Code)

**Relationship to Existing Three-Layer Architecture:**

The framework's CONFIG-DIRECTORY-PATTERN.md defines three layers. This ADR refines Layer 1:

| Layer | Owner | Contents | This ADR adds |
|-------|-------|----------|---------------|
| Layer 1: `.claude/` | Framework | agents/, skills/, settings.json | **+ CLAUDE.md, + rules/** |
| Layer 2: `config/` | User | Style guides, templates, preferences | No changes |
| Layer 3: Workspace dirs | User | daily/, projects/, entities/, etc. | No changes |

**Configuration Ownership by Repo:**

| Repo | Purpose | CLAUDE.md | rules/ | agents/ | skills/ |
|------|---------|-----------|--------|---------|---------|
| liminis | App development | App conventions, ADR index, git workflow | TypeScript, Electron main/renderer, pre-commit | None (agents owned by framework) | None |
| liminis-framework | Runtime framework | Amanuensis role, workspace structure, skill index, delegation | Daily notes, entities, ingestion, drafts, wiki conventions, work quality | daily-ops, meeting-analyst, drafting, entity-manager, file-ingestion | 33 domain skills |
| kiln | Dev scaffold | Project workflow, issue conventions | (as needed) | 7 codebase/research agents | 2 workflow skills |

**Evolution Guidelines:**
- When CLAUDE.md exceeds ~120 lines, extract path-specific content to `rules/`
- When a rule file exceeds ~60 lines, consider splitting by sub-scope
- When adding a new ADR that implies code patterns, add a corresponding rule (not inline in CLAUDE.md)
- Review `.claude/` configuration quarterly: remove stale rules, audit permissions, check for drift between repos
- New repos MUST start with at minimum: `CLAUDE.md` + `.claude/settings.local.json`

**Alternatives Considered:**
- Single monolithic CLAUDE.md per repo → Rejected: doesn't scale, loads irrelevant content for every interaction
- Keep AGENTS.md as primary config → Rejected: not auto-discovered by Claude Code; must be explicitly read
- Rules without path scoping → Rejected: loses the key benefit of contextual loading
- Centralized config at project root → Rejected: repos are independent git repositories with different concerns
- Rewrite framework skill/agent conventions → Rejected: existing conventions in AGENT-SKILLS-GUIDE.md are well-established and correct

**Consequences:**
- ✅ Path-scoped rules reduce prompt overhead (only relevant rules loaded per interaction)
- ✅ CLAUDE.md auto-loads — no more relying on explicit reads of AGENTS.md
- ✅ Preserves existing skill and agent conventions (no disruption to framework)
- ✅ Clear ownership: each repo's `.claude/` is self-contained and purpose-specific
- ✅ CLAUDE.md stays readable and maintainable at <120 lines
- ✅ Permissions are auditable and intentional (no accumulated cruft)
- ✅ Framework ships with sensible defaults; users can override via workspace rules
- ❌ More files to maintain (mitigated by clear naming and scoping)
- ❌ Must remember to update rules when ADRs change (mitigated by linking)
- ❌ Framework docs need updating to reflect CLAUDE.md and rules/ additions
