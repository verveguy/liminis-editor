# ADR-069: Claude Agent SDK SessionStore — Evaluation and Decision to Decline (issue #892)

**Status:** Declined  
**Date:** 2026-06-24  
**Issue:** [#892](https://github.com/verveguy/liminis/issues/892)

## Context

The Claude Agent SDK offers a `SessionStore` adapter that mirrors session transcripts to
a custom backend (S3, Redis, Postgres, or a bespoke adapter). By default the SDK writes
transcripts as JSONL under `~/.claude/projects/<cwd-hash>/<uuid>.jsonl`; a `SessionStore`
mirrors those writes to the adapter in real time. On resume, the SDK calls the adapter's
`load(key)` method (which returns transcript entries in-memory), then internally
materialises those entries to a temporary local directory (`claude-resume-<uuid>`) and
sets `CLAUDE_CONFIG_DIR` to that path before spawning the subprocess. The interface
requires `append(key, entries)` and `load(key)`; optional methods include `listSessions`,
`delete`, `listSubkeys`.

Issue #892 evaluated SessionStore for Liminis as a potential path to: workspace-local
transcript storage (ADR-005 alignment), session durability independent of the global
`~/.claude/` directory, conversation branching/fork UX, subagent transcript visibility,
and knowledge-graph capture via the `append()` callback.

The spec asked six questions: (1) Is there a compelling single-host use case? (2) How does
it relate to the chat-state-manager (ADR-004/ADR-032) and existing SDK resume? (3) Can
the `enableFileCheckpointing` conflict be resolved? (4) What are the implications of
redirecting `CLAUDE_CONFIG_DIR`? (5) What would a minimal workspace-local adapter look
like, and is the conformance suite sufficient to trust it? (6) Net recommendation?

## Constraints Found

1. **Hard SDK constraint — `sessionStore` + `enableFileCheckpointing` are mutually
   exclusive.** SDK 0.2.119 throws synchronously before spawning anything when both are
   present:
   ```
   enableFileCheckpointing is not yet supported with sessionStore (backup blobs are not
   mirrored, so rewindFiles() fails after a store-backed resume).
   ```
   The error message says "not yet supported" (implying possible future SDK support), but
   no timeline is known. Choosing SessionStore today means disabling
   `enableFileCheckpointing`, which in turn makes `rewindToCheckpoint()` and
   `CheckpointRestoration` dead code — a user-facing feature loss.

2. **ADR-068 already solves the core single-host durability problem.** The reseed
   iterator in `reseed-history.ts` rebuilds a synthetic SDK context from Liminis's own
   durable `entries[]` whenever the SDK JSONL is absent. SessionStore is an alternative
   mechanism for the same problem — but ADR-068's approach is already live, tested, and
   does not depend on the JSONL file existing at all. Two redundant mechanisms would
   accumulate maintenance debt without additional benefit.

3. **`SessionStore` is `@alpha`.** All SessionStore types in the SDK's `.d.ts` are
   marked `@alpha`. The API is subject to breaking changes without a semver major bump.
   A custom adapter written today creates maintenance debt against an unstable contract.

4. **Dual-write architecture — store adds a write, does not replace local JSONL.** The
   SDK subprocess writes local JSONL unconditionally; the `sessionStore.append()` fires
   after each batch as a best-effort mirror. Mirror failures produce `mirror_error`
   system messages and do not affect the subprocess. Adopting a store therefore adds a
   second write path without eliminating the first.

5. **`CLAUDE_CONFIG_DIR` redirect requires an explicit credential-handling strategy.**
   The SDK derives the projects directory from `CLAUDE_CONFIG_DIR` (defaults to
   `~/.claude`). Redirecting it to a workspace path would make raw JSONL workspace-local.
   Liminis's own credential detection (ADR-058 / `claude-agent.ts`) reads
   `~/.claude/.credentials.json` directly and is not affected by `CLAUDE_CONFIG_DIR`.
   However, the SDK subprocess's credential lookup when `CLAUDE_CONFIG_DIR` is redirected
   is not fully determined from SDK source — the subprocess may look for credentials
   relative to `CLAUDE_CONFIG_DIR`, which would mean credentials must either be present
   in the redirected path or symlinked there. Placing credentials inside a workspace path
   risks them landing in a version-controlled directory. No safe credential-handling
   strategy for this pattern has been designed.

6. **KG capture via `append()` receives raw JSONL, not structured `entries[]`.** The
   `append()` callback receives raw `{type: string, ...}` objects in SDK JSONL format.
   Liminis's knowledge-graph indexing pipeline already processes structured
   `ConversationEntry[]` objects. Feeding the pipeline from raw JSONL would require a
   new parser and produce lower-fidelity data than the structured entries that already
   exist.

## Decision: Decline

**Addressing each spec question:**

1. **No compelling single-host use case.** The headline SessionStore benefit — sharing
   transcripts across multiple hosts or autoscaled workers — does not apply to Liminis.
   Each speculative single-host use case is already covered by an existing, simpler
   mechanism: session durability is handled by ADR-068 reseed; workspace-local transcripts
   via `CLAUDE_CONFIG_DIR` redirect are blocked by the credential security concern;
   conversation branching works today via `forkSession: true`; KG capture is better
   served by structured `entries[]` already flowing through the pipeline; and subagent
   transcript visibility has no current user demand.

2. **Redundant with existing mechanisms; creates dual source-of-truth.** Liminis's
   `entries[]` (ADR-004/ADR-032) is the canonical durable representation. SDK JSONL is
   the raw API transcript format that the SDK manages internally. SessionStore would add
   a third representation — a mirrored copy of the raw JSONL — that must be kept
   consistent with both. ADR-068 already makes the absence of the JSONL survivable;
   there is no gap for SessionStore to fill without creating overlap.

3. **`enableFileCheckpointing` conflict not resolvable today.** The SDK throws
   synchronously; no workaround exists short of disabling checkpointing entirely. The
   `rewindToCheckpoint()` / `CheckpointRestoration` feature is user-facing (time-travel
   file restoration). Dropping it to gain SessionStore is not a trade-off the current
   feature set supports.

4. **`CLAUDE_CONFIG_DIR` redirect not safe to pursue.** Even without SessionStore, a
   `CLAUDE_CONFIG_DIR` redirect would make transcripts workspace-local. But credential
   exposure in a workspace path is a disqualifying concern. Cross-workspace session
   listing would also break. This is orthogonal to SessionStore and could be revisited
   independently only if a secure credential-handling strategy is designed first.

5. **Minimal adapter not worth building yet.** A conformance suite exists in the SDK
   repo, but the `@alpha` status, the checkpointing conflict, and ADR-068 coverage make
   it premature. The implementation cost and ongoing maintenance burden outweigh the
   speculative benefits.

6. **Net recommendation: Decline.** No follow-up implementation issue is created.
   Re-evaluate when any of the following conditions are met:
   - (a) The SDK removes the `sessionStore` + `enableFileCheckpointing` mutual-exclusion
     constraint (the "not yet supported" phrasing suggests this may come in a future
     release).
   - (b) `SessionStore` graduates from `@alpha` to a stable API.
   - (c) A genuine multi-source or cross-host use case emerges in Liminis that the
     current `entries[]` / ADR-068 reseed path cannot address.

## Alternatives Considered

**Adopt fully (disable `enableFileCheckpointing`).** Adopting SessionStore today requires
setting `enableFileCheckpointing: false`. This removes the `rewindToCheckpoint()` feature
and renders `CheckpointRestoration` dead code — an unacceptable regression with no
migration path for existing checkpoints. Rejected.

**Partial adoption — new sessions only, `enableFileCheckpointing` disabled for
store-backed sessions.** The same feature loss applies. Additionally, running two
session models simultaneously (store-backed new sessions, file-checkpoint old sessions)
creates the dual-source-of-truth problem without the compensating benefits. It also
requires conditional logic in `ClaudeAgentManager.run()` that would interact poorly with
the ADR-068 reseed guard. Rejected.

**`CLAUDE_CONFIG_DIR` redirect without SessionStore.** Redirecting `CLAUDE_CONFIG_DIR`
to a workspace path (e.g., `.liminis/claude-data/`) is orthogonal to the SessionStore
question — it is a pure filesystem redirect, not an adapter. It would make raw JSONL
workspace-local and is worth revisiting independently if a secure credential-handling
path can be designed (credentials cannot be placed inside a workspace path that is likely
version-controlled). Not rejected permanently; deferred pending a security design.

## Consequences

**Positive:**
- No new complexity. The existing ADR-068 reseed path remains the sole durability
  mechanism, and the `enableFileCheckpointing` / `rewindToCheckpoint()` feature is
  preserved without change.
- No `@alpha` API maintenance burden. If the SDK changes the SessionStore interface
  in a future minor release, Liminis is not affected.
- Single source of truth maintained. `entries[]` remains authoritative; no second
  transcript representation to keep consistent.

**Negative:**
- Raw SDK JSONL stays in `~/.claude/projects/` (not workspace-local). Conversations
  are not portable by directory alone; `entries[]` JSON remains the portable
  representation.
- No SDK-native session listing from a custom store. Features like listing sessions
  by workspace or browsing subagent transcripts via SDK APIs are not available.

**Neutral:**
- Neither workspace-local JSONL nor KG capture via `append()` are delivered by this
  decision. Both remain possible through other paths (a future `CLAUDE_CONFIG_DIR`
  design; feeding KG from `entries[]` directly) that do not depend on SessionStore.
