# ADR-072: Catch Up — Retry Indexing Jobs Orphaned by Transient Failures (issue #922)

**Status:** Accepted
**Date:** 2026-07-17
**Issue:** [#922](https://github.com/verveguy/liminis/issues/922)

## Context

The context-graph indexing queue (`IndexingQueue`, `liminis-app/src/main/indexing-queue.ts`)
tracks each job (one content chunk, or a legacy whole-file entry) with a per-target status —
`pending` / `processing` / `completed` / `failed` — an attempt count, and a retry-backoff
timer. `markFailed()` gives a job up to `MAX_ATTEMPTS` (6) retries with a total backoff span
of ~17 minutes before settling it into `failed`.

A ~54-minute network outage reaching the extraction LLM caused 38 chunks across 8 files to
exhaust their retry budget and land in `failed`, with no way to retry them short of a full
**Rebuild** — a disproportionate fix (re-indexes the entire workspace, full extraction-LLM
cost) for recovering a handful of files. Two pre-existing defects made this worse than "just
retry the failed ones":

1. **Queue compaction conflated `failed` with `completed`.** `isFullyComplete()` (the
   predicate gating what `compact()` purges) treated both statuses as terminal/purgeable.
   `compact()` runs on every app shutdown (`stop()`, whenever `completedCount > 0`) and
   mid-session after 500 completions. In practice, essentially any restart after at least
   one successful index run would erase every `failed` queue record on the next `stop()` —
   the only record identifying which chunks needed recovery.
2. **Chunk-level state is written speculatively at enqueue time.** `enqueueFileChange()`
   calls `ChunkStateStore.setEntry()` as soon as a chunk is diffed as new/changed, before
   it's processed — regardless of whether processing later fails. A subsequent content-diff
   scan (`Update Index`) sees the speculative record, concludes "no change," and silently
   skips the chunk, even though the queue still shows it `failed`. (The legacy whole-file
   path doesn't have this problem: `ContentHashIndex.set()` there only runs after success.)

Combined, a `failed` job could become invisible to *both* the queue (once compacted) and any
future diff-based rescan (once its chunk-state record claims it's current) — with no error,
no badge, and nothing for a human to notice.

## Decision

Add a "Catch Up" action (`IndexingQueue.catchUp()`, exposed via `contextGraph:catchUp` /
`contextGraph:getCatchUpState` IPC handlers and a button in `ContextGraphPanel.tsx`) that
resets eligible jobs to retryable and hands them back to the existing queue processor —
without a rescan, without touching `ChunkStateStore`, and without clearing the graph.

**1. Redefine "purgeable" instead of adding a new terminal state.** `isFullyComplete()` is
renamed to `isPurgeable()` and redefined from "completed or failed" to **completed only**.
All four call sites (`load()`, `markCompleted()`, `compact()` ×2) already delegated to this
one predicate, so this single change is the entire compaction fix — `failed` entries now
survive both the mid-session and shutdown compaction paths, and `completedCount`'s dual role
(terminal-entry counter *and* the threshold that gates `compact()`) resolves for free since
it now only ever counts what `compact()` actually removes. This also means Catch Up never
needs to touch `ChunkStateStore` for the primary case: since the original `failed` entry (and
its own stored `content`/`chunk_id`/`chunk_version_hash`) survives, resetting it to `pending`
and letting the normal processor pick it up bypasses `diffChunks()` entirely — there's no
speculative chunk-state record left to reconcile.

**2. Resolve superseded duplicates by direct status flip, not a queue-format extension.**
Because `chunk_id` is stable across edits but `chunk_version_hash` changes, editing a file
again after a chunk's job failed produces a second queue entry with the same `chunk_id`. If
Catch Up blindly reset the *original* failed entry, it could reprocess stale content out of
order relative to a newer entry that already completed with fresher content — a contradictory
episode. `catchUp()` builds a `Map<chunk_id ?? filePath, entry>` in a single forward pass over
`this.entries` (always populated in creation order, so the last write per key is the newest);
only the entry that map identifies as canonical for its key is ever retried. Older
failed/stale-processing entries sharing a key with a newer one are instead marked `completed`
with an explanatory `lastError`, so they stop being counted and get swept up by the next
`compact()`.

**3. FR-010 ("stale processing") is scoped to detection + reset only — no RPC timeout.** A
`processing` entry whose `lastAttemptAt` is older than `STALE_PROCESSING_THRESHOLD_MS` (10
minutes — comfortable headroom over the tens-of-seconds a single processing attempt should
take, while still well under the ~17-minute total retry-backoff span for a *failed* job, so it
can't be confused with an entry that's merely mid-retry) is folded into
the same eligibility check as `failed` entries and reset the same way. This recovers the
common case (an entry orphaned by, e.g., an app crash mid-request) but has a known limitation:
`processContextGraphItem()`'s single-flight `isProcessing` guard means a *genuinely* hung
`processChunk`/`processDocument` RPC (no per-call timeout exists in
`context-graph-socket-client.ts`) will keep blocking the whole processing loop even after
Catch Up flips the entry back to `pending` — it only actually resumes once that call errors
or the app restarts. A hard timeout around the RPC call would close this gap but is a
materially larger, separate change to the socket client; deferred as a follow-up, consistent
with the spec's "MAY" framing for this P3 requirement.

**4. `markFailed()` now also calls `sendBacklogState()` (in addition to the new
`sendCatchUpState()`).** It was previously the only status-mutating path that never notified
the renderer, so `backlogCount` went stale by one the moment a job exhausted retries and
stopped counting as "pending." `sendCatchUpState()` — a dedicated
`contextGraph:catchUpStateChanged` push channel, not folded into `backlogStateChanged`, since
backlog (pending-awaiting-schedule) and catch-up-eligible (failed/stale-awaiting-user-action)
are different concerns — is wired into every site that can change the eligible count:
`markFailed()`, `markCompleted()`, `markAborted()`, both enqueue paths, `checkBacklogTransition()`,
and the existing 60s `checkScheduleTransition()` tick (the only place that notices *pure*
time-elapsed staleness, since nothing else triggers a push when a `processing` entry merely
gets older).

## Alternatives Considered

**Separate `resolved` sub-flag on `TargetStatus` instead of redefining "purgeable."**
Rejected: unnecessary complexity for a fix this narrow — every consumer of "is this entry
done with" already funneled through one predicate.

**Leave superseded duplicates as `failed` forever, or add a tombstone/delete record type.**
Rejected: the former violates SC-003 ("count always matches the true current number of
eligible jobs" — a duplicate that will never actually be retried shouldn't count forever);
the latter is an unneeded queue-format change for a narrow timing-window edge case.

**Add a hard RPC timeout to unstick a genuinely hung `processChunk`/`processDocument` call
live, as part of this issue.** Rejected for now: FR-010 is explicitly P3/"MAY" in the spec,
and the timeout mechanism (mirroring the existing `CONTEXT_GRAPH_PROBE_TIMEOUT_MS` /
`Promise.race` pattern used for the `status()` probe) is a materially larger, independently
reviewable change to `context-graph-socket-client.ts`. Scoping Catch Up to detection + reset
delivers the primary (`failed`-job) recovery path this issue exists for without coupling it
to that larger change.

## Consequences

**Positive:**
- A transient outage affecting dozens of chunks is now recoverable with one click plus normal
  queue processing, instead of a full Rebuild (SC-001).
- `failed` queue entries survive app restarts and periodic compaction going forward — the
  compaction bug described in Background no longer silently erases failure records.
- Already-`completed` work is never touched or duplicated (FR-002/SC-002); no graph-clearing
  or full-rescan operation is part of Catch Up (FR-005/SC-004).

**Negative / Forward-looking constraint:**
- **This fix is forward-looking only.** Workspaces where a `failed` entry was already purged
  under the old (buggy) compaction behavior have no surviving record to recover — there is no
  retroactive fix possible from queue state alone.
- **FR-010's live-unstick behavior is incomplete by design** (see Decision point 3): a Catch
  Up reset of a stale-`processing` entry doesn't interrupt an RPC call that's actually still
  hung, only one that's already errored or the process already lost track of. Closing this
  gap requires the RPC-timeout follow-up flagged above.

**Neutral:**
- The periodic 60s `sendCatchUpState()` tick adds a small O(n) scan over queue entries purely
  to catch pure time-elapsed staleness; acceptable at the spec's stated scale ("hundreds of
  jobs"). If real workspaces routinely carry far more queue entries, this scan would need
  memoizing instead of full recomputation per tick.
