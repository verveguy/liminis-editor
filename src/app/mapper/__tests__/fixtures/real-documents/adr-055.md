# ADR-055: Atomic, Serialized Settings Persistence (2026-04-21)

> Hardens `settings.json` against concurrent-write data loss and crash-induced truncation.

**Context:**

- `settings.json` persistence was lossy under concurrent writes. Keys (`workspaceRoot`, `windowBounds`) disappeared silently because multiple async handlers each read a stale snapshot of settings, then wrote their own partial merge, overwriting each other's changes.
- Non-atomic writes (truncate-then-write) left a corrupt or empty file if the app was killed mid-write. The parse-error fallback silently returned `{}`, causing the next write to overwrite all prior settings with a single key.
- A burst of concurrent state-change events (e.g., from framework upgrades, service restarts, or window resize during splash-to-main transition) reproduced the race cleanly.

**Decision:**

Introduce a `SettingsPersistence` class (`main/settings-persistence.ts`) with three guarantees:

1. **In-memory authoritative cache**: Settings are read from disk once at startup (`initialize()`). All subsequent reads return a copy of the in-memory cache — never disk. This eliminates the stale-snapshot race.

2. **Synchronous patch application (`applyPatch`)**: Cache updates are applied synchronously (no `await` before the merge). This makes the read-modify-write sequence within a single JS turn — atomic from the JS event loop's perspective. All writers must use `applyPatch(patch)` (exposed as `updateSettings` in injection interfaces), not the old `loadSettings() + spread + saveSettings()` pattern.

3. **Atomic disk writes + serialized write queue**: Each disk write is: (a) serialized through a promise-chaining queue so no two writes execute concurrently, and (b) implemented as `writeFile(tmp)` → `rename(tmp, settings)`. `rename(2)` is atomic on POSIX (macOS primary target) — crash mid-write leaves `settings.json` intact.

**The old pattern (prohibited):**
```typescript
// BROKEN — two concurrent callers both read the same stale snapshot
const settings = await loadSettings()
await saveSettings({ ...settings, myKey: value })
```

**The correct pattern:**
```typescript
// CORRECT — cache update is synchronous; no stale snapshot possible
await context.updateSettings({ myKey: value })
```

**Interfaces updated:**
- `HandlerContext` (`ipc/types.ts`): `updateSettings: (patch: Record<string, unknown>) => Promise<void>` added
- `WindowDependencies` (`window/create-window.ts`): `updateSettings` added; `saveSettings` removed
- `ScheduledTaskManagerDependencies` (`scheduled-task-manager.ts`): `updateSettings` added
- `IndexingQueue.setDependencies` (`indexing-queue.ts`): `updateSettings` added

**Startup `.tmp` cleanup**: On startup, if `settings.json.tmp` exists (left from a previous crashed write), it is deleted before loading. The rename never happened, so `settings.json` is intact.

**Error handling on parse failure**: If `settings.json` exists but cannot be read or parsed, a `warn`-level log is emitted and the fallback is `{}`. Silent swallowing of parse errors is prohibited.

**Alternatives considered:**

- **`write-file-atomic` npm package**: Identical pattern, well-tested, but adds a dependency. Inline implementation is 3 lines and avoids the dependency.
- **Synchronous `loadSettings()`**: Would require updating 15+ `await loadSettings()` call sites across 7 files. The `applyPatch` approach is additive — existing signatures are preserved.
- **`electron-store` or SQLite**: Out of scope; no format migration required.

**Consequences:**

- All future settings writers **must** use `updateSettings(patch)`. Using `loadSettings() + spread + saveSettings()` will silently reintroduce the race and violates this ADR.
- `loadSettings()` and `saveSettings()` are kept in `HandlerContext` for startup-time and full-object-replace callers, but should not be used for partial key writes.
- The in-memory cache invariant must be preserved: `initialize()` must be awaited before any IPC handler processes `settings:get` or `settings:set`.
