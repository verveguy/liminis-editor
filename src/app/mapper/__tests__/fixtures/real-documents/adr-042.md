# ADR-042: Context Graph Concurrent Read/Write Architecture (2026-03-01, updated 2026-03-17)

**Context:**
- The context graph MCP server (ADR-035) blocks all operations while a document is being indexed (10-45 seconds per document)
- This blocking occurs because the `McpDirectInvoker` tracks `inFlight` operations per stdio server
- When a user queries the knowledge graph during background indexing, the query is blocked until indexing completes
- This creates a poor user experience where knowledge graph queries appear unresponsive during workspace indexing

**Spike Test Validation:**
Before implementing this architecture, a spike test validated that concurrent access was technically feasible:

| Metric | Result |
|--------|--------|
| Read completion time | 0.09-0.11s |
| Write completion time | 66.1s |
| Concurrent reads during write | 3 successful |
| Database errors | None |
| Data corruption | None |

Key findings:
- FalkorDBLite supports concurrent reads from multiple asyncio tasks in the same process
- Graphiti library is safe for concurrent `search()` + `add_episode()` calls
- LLM extraction naturally yields to asyncio (90%+ of time spent in I/O)
- Asyncio tasks interleave properly during LLM I/O waits

**Decision:**
Split the single context graph MCP server into two separate servers with shared state:

1. **`knowledge-reader`**: Exposes 6 read-only tools that query the knowledge graph without mutations
2. **`knowledge-writer`**: Exposes 7 write tools that mutate the knowledge graph

Both servers forward tool calls to the underlying stdio MCP servers via `McpDirectInvoker`. This allows read operations to proceed independently of write operations.

**Implementation Details:**

| Component | File | Purpose |
|-----------|------|---------|
| Reader wrapper | `src/main/context-graph-reader-mcp-server.ts` | In-process wrapper forwarding to reader stdio |
| Writer wrapper | `src/main/context-graph-writer-mcp-server.ts` | In-process wrapper forwarding to writer stdio |
| Agent registration | `src/main/claude-agent.ts` | Registers both wrappers, auto-approves |
| Indexing queue | `src/main/indexing-queue.ts` | Uses writer for mutations, reader for status |

**Key Design Decisions:**

1. **In-process wrapper pattern (ADR-037)**: Both servers use the established pattern where the SDK calls an in-process wrapper that forwards to the app's managed stdio server. This prevents the SDK from spawning duplicate processes.

2. **Both servers auto-approved**: Since they're logically one service split for concurrency, both are automatically approved without user confirmation.

3. **Workspace directory renamed to `.lcg/`**: The workspace data directory was renamed from `.graphiti/` to `.lcg/` as part of the Liminis Context Graph rename (liminis-graph#59). The binary's auto-migration renames `.graphiti/` → `.lcg/` on first startup against a legacy workspace. Tool schemas remain identical.

4. **No external dependencies**: FalkorDBLite remains embedded (port 16379). No Docker or external FalkorDB required.

**Alternatives Considered:**

- **Single server with request queuing**: Rejected because reads would still block behind long-running writes; doesn't solve the core problem.
- **External FalkorDB service**: Rejected because it adds deployment complexity (Docker) contrary to the "turnkey" design goal.
- **Thread-based concurrency**: Rejected because the existing codebase uses asyncio throughout; mixing would add complexity.
- **Read-through caching**: Rejected because Graphiti's temporal awareness means cached data could become stale during writes.

**Consequences:**

- Read operations proceed during writes: Queries return results even while document indexing is in progress
- Single FalkorDBLite instance: Embedded database remains self-contained (no external services)
- Two MCP servers registered: `knowledge-reader` and `knowledge-writer` both auto-approved
- Indexing queue uses writer: Background indexing calls `knowledge-writer` tools
- Tool schemas must be kept in sync between Python servers and TypeScript wrappers
- Adding new tools requires updates in both the Python server and TypeScript wrapper
