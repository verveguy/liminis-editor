# ADR-071: Drop DOMPurify Sanitization from Raw-HTML Round-Trip Import (issue #909)

**Status:** Accepted
**Date:** 2026-07-12
**Issue:** [#909](https://github.com/verveguy/liminis/issues/909)

## Context

Raw HTML embedded in markdown (mdast `html` nodes, both block-level and inline/phrasing)
was not preserved through the app's parse -> import -> export -> stringify pipeline.
Block-level HTML (e.g. a `<div>` wrapping other markup) lost its tags and attributes
entirely on import, keeping only the extracted inner text. Inline HTML (e.g. a `<span>`)
survived as an ordinary text node but had its angle brackets escaped on export, turning
live markup into literal `\<tag>` text.

The pre-existing import path (`convertHtml` in `mdastToLexical.ts`) ran all block-level
HTML through `DOMPurify.sanitize()` with a hand-maintained tag/attribute allowlist before
extracting `doc.body.textContent` into a plain paragraph. Sanitization existed because the
extracted content was eventually rendered into the live editor DOM as ordinary text/element
nodes — a genuine XSS surface if the sanitizer were ever bypassed or the extraction path
changed to use `innerHTML`.

Fixing #909 required a Lexical node capable of carrying the complete original markup
(tags, attributes, nesting) through the pipeline opaquely, modeled on the existing
`DecoratorNode` pattern used for equations, mermaid diagrams, and footnotes (ADR-002).

## Decision

Introduce `HtmlNode`, a `DecoratorNode` (block via `inline: false`, phrasing via
`inline: true`) that stores the raw HTML string verbatim and **never sanitizes it**.
`HtmlNode.createDOM()`, `decorate()`, and `exportDOM()` all assign the stored string via
`textContent` (React child / DOM text), never via `innerHTML` — so arbitrary markup,
including `<script>` tags, renders as inert visible text rather than executable DOM.
DOMPurify and its allowlist are removed entirely from the block-level `convertHtml` import
path; the untrimmed `node.value` is stored as-is (a trimmed copy is only used for sniffing
the pre-existing dimensioned-`<img>` and equation special-cases, which are preserved
unchanged since they are matched, load-bearing pairs with `convertImageNode` on export).

**Why removing sanitization is safe:** the only reason DOMPurify existed at this boundary
was to protect a rendering path that assigned extracted content into the live DOM as
ordinary editable content. That rendering path no longer exists for this content — post-fix,
raw HTML is displayed exclusively as inert text via `textContent`. Sanitizing text that is
never interpreted as markup has no security benefit and directly conflicts with the
feature's "preserve in full" requirement (the old allowlist would silently strip any tag or
attribute not on it, which is precisely the data loss #909 reports).

## Alternatives Considered

**Keep DOMPurify as defense-in-depth, sanitize before storing in `HtmlNode`.** Rejected:
sanitizing before storage directly reintroduces the original bug — an allowlist-based
sanitizer strips anything outside its allowed tags/attributes, which is exactly the lossy
behavior #909 reports. Defense-in-depth only makes sense if there is a plausible path from
stored content to live DOM; today there is none.

**Sanitize only at render time (`decorate()`), keep the full string in storage.** Rejected
as unnecessary complexity: `decorate()` and `createDOM()` use `textContent`, which cannot
execute markup regardless of content — sanitizing immediately before a `textContent` assignment
protects against nothing.

## Consequences

**Positive:**
- Raw HTML (block and inline) round-trips byte-identical, satisfying FR-001–FR-004.
- ~60 lines of allowlist/fallback/textContent-extraction logic removed from
  `convertHtml`, replaced by a single opaque-preservation path.
- The dimensioned-`<img>` special case (paired with `convertImageNode` on export) is
  unaffected — it is now fed from a bare `DOMParser` parse instead of DOMPurify's output,
  which does not execute scripts and reads only specific attributes as strings.

**Negative / Forward-looking constraint:**
- **If a future feature renders preserved `HtmlNode` content live in the WYSIWYG view
  (e.g., an actual rendered preview instead of inert text), sanitization must be
  reintroduced at that new rendering boundary before any `innerHTML`-style assignment.**
  This ADR intentionally removes sanitization only because the current consumer
  (`textContent`) cannot execute markup — that invariant is what makes the removal safe,
  and it must be re-established if the consumer ever changes.
- Content previously routed to an inert `$createCodeNode('html')` fallback (e.g. HTML that
  DOMPurify would have stripped entirely) is now preserved as opaque `HtmlNode` text
  instead — a strict fidelity improvement, but a behavior change worth flagging since no
  fixture in the pre-existing corpus depended on the old strip-to-code-block behavior.

**Neutral:**
- `<hr>` and standalone `<br>` special-cases (previously untested, already-lossy) are
  folded into the same generic opaque-preservation path, which strictly improves their
  fidelity (attributes now preserved) at no risk, since no fixture exercised them before.
