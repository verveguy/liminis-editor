# ADR-053: Service Registry and Tiered Startup for Non-Blocking Splash Close (2026-04-18)

**Context:**

- Before this change, `createWindow()` in `src/main/index.ts` sequentially awaited every main-process service: `startLocalInference` → `initializeMcpServers` → `initializeContextGraphService` → `prewarmMcpServers` → `indexingQueue.start` → `indexingQueue.startScheduleChecker`. The splash window remained visible until `loadRenderer()` fired `ready-to-show` on the main window — typically **~5.8 s** on a warm cache and **30 s+** when `uv` was downloading graphiti packages.
- The slowest core dependency was `context-graph-service`, which spawns a Python subprocess under `uv run graphiti_service.py`. Nothing in the splash-gating path actually depends on the context graph being ready before the user can interact with the app.
- `before-quit` contained a manually ordered shutdown that enforced implicit dependencies: MCP clients disconnect first (so the context graph's socket has no writers), then file/clip/remote servers, then context-graph-service, then local-inference. Any reordering silently broke clean teardown (broken-pipe logs, orphaned processes).
- Phase 1a (#628 / PR #634) landed a `ServiceRegistry` core module with `register`, `startAll` (topological, concurrent, deps awaited via `whenReady`), `shutdownAll` (Kahn-decomposed reverse-topo levels), and `whenAllCoreReady({timeoutMs})`. Nothing consumed it.

**Decision:**

Wire every main-process service into `ServiceRegistry` with an explicit **tier** (`core` vs `deferred`) and dependency list. The splash closes as soon as `whenAllCoreReady()` resolves; deferred services continue starting in the background. Shutdown collapses into a single `registry.shutdownAll({ timeoutMs: 70_000 })` whose reverse-topological order reproduces the pre-change manual sequence.

The 70 s budget is derived from the sequential level costs: level-0 (~2 s) + context graph `SHUTDOWN_TIMEOUT_MS` (60 s, raised by ADR-052 for WAL checkpoint) + local-inference `SHUTDOWN_TIMEOUT_MS` (5 s) + buffer (3 s) = 70 s. **Do not reduce this value without also reducing `context-graph-lifecycle.ts:SHUTDOWN_TIMEOUT_MS`**, or local-inference will be orphaned on slow context graph teardown.

**Tier taxonomy:**

- **`core`** — gates splash close. Fast-starting, latency-sensitive, no network or subprocess spawn. Today: `file-server`, `clip-server`, `file-watcher`, `chat-state-manager`, `mcp:actions`, `mcp:workflow`, `mcp:liminis-app`.
- **`deferred`** — runs in the background after splash has closed. Covers anything that spawns a subprocess, downloads packages, or otherwise blocks for seconds. Today: `local-inference`, `leann-indexer`, `context-graph-service`, `mcp:semantic-search`, `mcp:knowledge-reader`, `mcp:knowledge-writer`, `mcp:remarkable`, `indexing-queue`.

A service failure never promotes a dependent from `deferred` to `failed-blocking-splash`. If `context-graph-service` fails to start, its dependents (`mcp:knowledge-reader`, `mcp:knowledge-writer`, `indexing-queue`) transition to `failed` without ever entering `start()` — the splash has already closed.

**Per-service `start` / `stop` contract:**

Every registration supplies idempotent async `start` and `stop` hooks.

- `start()`:
  - Must resolve only once the service is fully ready for use. Spawn-and-forget is not sufficient.
  - Should be idempotent when called after a previous `start()` failure — rare today but required once workspace-switch restart lands.
  - Settings-gated services (e.g. `clip-server`) resolve `ready` with `registry.setMessage(id, 'disabled')` rather than throwing, so the registry keeps the entry visible and core-ready isn't blocked.
- `stop()`:
  - Emits `log.info('shutdown-order', { id })` before side-effectful teardown, so reverse-topo order is verifiable from logs.
  - Handles the "never started" case quietly.

**Splash-close gate:**

```ts
registerAllServices({ workspaceRoot, getMainWindow, leannIndexer, indexingQueue, ... })

void registry.startAll()                             // fire-and-forget

try {
  await registry.whenAllCoreReady({ timeoutMs: 15_000 })
} catch (err) {
  log.error('Core services did not become ready in time', { err })
  // fall through — splash still closes, degraded state surfaces in Phase 3 UI
}

await loadRenderer(mainWindow)                       // triggers ready-to-show → closeSplash
```

On core-ready timeout the splash still closes. The renderer detects degraded state via the new `services:stateChanged` IPC channel (Phase 3 consumer).

**Shutdown guarantee:**

Reverse-topo levels from the current dep graph:

```
Level 0 (no dependents):  all mcp:*, indexing-queue, file-server, clip-server,
                          file-watcher, chat-state-manager
Level 1:                  context-graph-service
Level 2:                  local-inference, leann-indexer
```

This matches the pre-change manual order exactly: MCP clients stop first (so the context graph has no readers/writers), then the file/clip/remote servers and chat-state-manager in parallel, then context-graph-service, then local-inference. The `shutdown-order` log line in each `stop()` lets manual verification compare actual runtime order against this contract.

**IPC surface for registry state:**

New channels (ADR-007 / ADR-032 pattern):

- `services:getAll` — one-shot snapshot of every `ServiceState`
- `services:stateChanged` — push from main on every registry `change` event, broadcast to the main window only (follows `contextGraph:pauseStateChanged` precedent)

Exposed in the preload as `api.services.getAll()` and `api.services.onStateChanged(cb)`. No renderer UI consumer exists yet; the Phase 3 status indicator will subscribe.

**What stays inline (not in the registry, this phase):**

- `remote-session` server — settings-gated, generates a token, writes `.liminis/api.env`
- `remarkable-sync-watcher` — no clean stop primitive exposed today
- `scheduled-task-manager` — depends on an initialized `chatStateManager` and workspaces conditionally
- `workspace-env` writer / remover (`writeWorkspaceEnv` / `removeWorkspaceEnv`)
- Broadcasting setup/cleanup (`setupRemoteSessionBroadcasting` / `cleanupRemoteSessionBroadcasting`)
- `claudeAgentManager` shutdown

These services run alongside the registry and are torn down manually before `registry.shutdownAll()`. They are candidates for a Phase 2 migration once the pattern proves out.

**Consequences:**

Positive:
- **Fast launch.** Splash closes in ~0.5 s even when graphiti is downloading packages on a cold `uv` cache. Target reduction from ~5.8 s → ~0.5 s.
- **Explicit dep graph.** `dependsOn` in `registrations.ts` is the single source of truth; previously-implicit ordering (knowledge-reader/writer → context graph) is now explicit and enforced by the registry.
- **Verifiable shutdown.** `shutdown-order` logs let any regression in reverse-topo ordering be caught in one launch/quit cycle.
- **Phase 3-ready state surface.** Renderer can already subscribe to registry state — a status indicator UI adds no new main-process code.

Negative / trade-offs:
- **Single-shot `startAll`.** `registerAllServices` + `startAll` can only run once per process. Workspace switch (Phase 2) needs a `registry.restart()` or a full registry rebuild.
- **Degraded state invisible for now.** On core-ready timeout the splash closes but there's no UI to surface "context graph failed to start." The Phase 3 status indicator will close this gap.
- **Two lifecycle systems.** Registry-managed services and inline services coexist. Until the Phase 2 migration consolidates, a contributor adding a new service has to decide which lane it belongs in.
- **`mcpDirectInvoker` surface grew.** A new `shutdownServer(name)` was needed to preserve per-service reverse-topo stop semantics (previously one atomic `shutdownAsync()` shut down all stdio clients in parallel).

**Migration / follow-ups:**

- Phase 2 should migrate `remote-session`, `remarkable-sync-watcher`, `scheduled-task-manager`, and `claudeAgentManager` into the registry, plus add workspace-switch restart semantics.
- Phase 3 should add a renderer status indicator consuming `services:*` IPC channels and surface the core-ready-timeout degraded state.

**Related ADRs:**

- **ADR-007** — IPC via `contextBridge` / `ipcMain.handle` pattern for the new `services:*` channels.
- **ADR-032** — Main process owns all state; renderer is reactive. Registry state is main-owned; renderer subscribes.
- **ADR-033** — Modular main process extraction. This ADR extends that pattern to lifecycle orchestration.
- **ADR-026** — macOS code signing and detached subprocesses. Shutdown escalation in `mcpDirectInvoker.shutdownServer` preserves the existing SIGTERM → SIGKILL semantics unchanged.
