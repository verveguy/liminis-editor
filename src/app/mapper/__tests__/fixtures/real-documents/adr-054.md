# ADR-054: Marp Presentation Support Architecture (2026-04-22)

**Context:**

- Liminis users want to author Marp markdown presentations (files with `marp: true` frontmatter) inside Liminis, with live slide preview, slide navigation, and export to HTML, PDF, and PPTX.
- Three architectural questions required explicit decisions before implementation:
  1. **Where does the presentation view live?** — separate window (à la ADR-039 graph visualizer) vs. inline editor toggle.
  2. **Should WYSIWYG mode be available for Marp files?** — the Lexical ↔ mdast pipeline (ADR-010) does not preserve HTML comment directives (`<!-- _class: lead -->`), so WYSIWYG editing corrupts per-slide Marp directives.
  3. **How should PPTX export be implemented?** — Marp CLI subprocess (requires system Chrome/Edge, complicates macOS notarization per ADR-050) vs. in-process screenshot assembly using Electron's `capturePage` + `pptxgenjs`.

**Decision 1 — Presentation view is an inline editor toggle, not a separate window:**

`EditorColumn.tsx` refactors its `isRawMode: boolean` to `viewMode: 'wysiwyg' | 'raw' | 'presentation'`. The Presentation toggle button appears in the existing editor button bar only when `isMarpFile` is true (detected via `/^---[\r\n][\s\S]*?[\r\n]marp:\s*true[\s\S]*?[\r\n]---/` frontmatter regex). The `MarpViewer` component renders in place of the editor content area when `viewMode === 'presentation'`.

This is a deliberate divergence from ADR-039 (which established separate windows for independent tool views like the knowledge graph visualizer). Presentation mode is a *document view mode* — it displays the same file being edited, not an independent tool. Opening it in a separate window would break the live-update requirement (edits would need to propagate across windows) and impose a mode-management burden (which window owns focus?). An inline toggle is both simpler and correct.

**Decision 2 — WYSIWYG mode remains available for Marp files, with a user-visible warning:**

The spec user explicitly requested both Lexical WYSIWYG and raw markdown editing for Marp files. WYSIWYG is therefore not disabled. However, the known round-trip limitation (ADR-010) is surfaced as a tooltip on the WYSIWYG mode button: "Editing in rich text mode may alter per-slide Marp directives (HTML comments)."

When a Marp file is first opened, `viewMode` defaults to `'raw'` (not `'wysiwyg'`) to avoid accidental directive corruption. A `useEffect` resets `viewMode` back to `'raw'` whenever `isMarpFile` transitions from true to false (e.g., frontmatter edited to remove `marp: true`) while in Presentation mode.

**Decision 3 — PPTX export via in-process screenshot assembly (`capturePage` + `pptxgenjs`):**

PPTX slides are captured one at a time using a hidden `BrowserWindow` (1280×720) loaded with the Marp HTML. For each slide, `executeJavaScript` toggles visibility on the relevant `<section>`, then `webContents.capturePage()` grabs a `NativeImage`. All images are assembled into a `.pptx` file using `pptxgenjs` with `LAYOUT_16x9`.

This avoids:
- Bundling a Chromium/Chrome binary (Marp CLI subprocess approach)
- System Chrome discovery at runtime (fragile on macOS)
- macOS notarization complications for unsigned subprocess binaries (ADR-050)

The trade-off is more implementation code and timing sensitivity (a 50ms per-slide pause is needed for CSS to apply after `executeJavaScript`). The resulting PPTX contains image-based slides (non-editable by default). A follow-up issue tracks editable PPTX via LibreOffice.

**Live rendering architecture:**

`MarpViewer` calls `window.api.marp.render({ markdown })` (IPC to main process) on every `currentContent` change. The main process uses `@marp-team/marp-core` (Node.js) to produce `{ html, css }`, which the renderer assembles into an `<iframe srcDoc>`. Rendering in the main process is required because `@marp-team/marp-core` is a CommonJS module that uses Node.js APIs, which are unavailable in the sandboxed renderer (`sandbox: true, nodeIntegration: false`).

Slide navigation uses `postMessage` from the React component to the iframe script, avoiding `allow-same-origin` on the iframe sandbox.

**New IPC surface:**

- `marp:render` — `{ markdown }` → `{ html, css }` for live preview
- `marp:exportHtml` — `{ markdown, title }` → save dialog → write `.html`
- `marp:exportPdf` — `{ markdown, title }` → hidden BrowserWindow → `printToPDF` → save `.pdf`
- `marp:exportPptx` — `{ markdown, title }` → hidden BrowserWindow → per-slide capture → pptxgenjs → save `.pptx`

All exposed as `window.api.marp.*` via the contextBridge (ADR-007 pattern).

**Consequences:**

Positive:
- Zero external runtime dependencies — no system Chrome, no Marp CLI, no LibreOffice.
- Presentation mode is contextual — it appears only when `isMarpFile`, keeping the editor UI clean for non-Marp files.
- All three export formats (HTML, PDF, PPTX) work offline and from a packaged Electron app.
- Live preview updates on every content change without manual refresh.

Negative / trade-offs:
- PPTX slides are image-based (non-editable). Editable PPTX requires LibreOffice; tracked as a follow-up.
- PPTX export is slow for large decks (~50ms per slide + capture overhead).
- WYSIWYG editing of Marp files can corrupt per-slide HTML comment directives. Mitigated by defaulting to Raw mode on open and surfacing a tooltip warning on the WYSIWYG button.
- One IPC round-trip per live-preview update (main process render). For typical typing cadence this is imperceptible, but very rapid edits (e.g., AI agent streaming) may cause queued renders.

**Related ADRs:**

- **ADR-007** — IPC via `contextBridge`. New `window.api.marp.*` domain follows this pattern.
- **ADR-010** — Bidirectional Markdown Conversion. Per-slide HTML comment directives are not preserved through the Lexical round-trip; this is the root cause of the WYSIWYG limitation documented above.
- **ADR-014** — Hidden Window PDF Generation. Marp PDF export extends this pattern with slide-sized page dimensions (1280×720px, landscape).
- **ADR-032** — Main process owns state. Marp rendering is a display concern handled in the main process; the renderer is purely reactive.
- **ADR-039** — Knowledge Graph Visualizer (separate window pattern). This ADR explicitly diverges from ADR-039 for the reasons described above.
- **ADR-050** — macOS Code Signing and Notarization. The choice to avoid Marp CLI subprocess was driven by notarization concerns documented here.
