# ADR-068: Session Durability — Reseed from Durable Entries When SDK Session Is Absent (issue #872)

**Status:** Accepted  
**Date:** 2026-06-23  
**Issue:** [#872](https://github.com/verveguy/liminis/issues/872)

## Context

Liminis persists chat history in `conversations/<chatId>.json` as `entries[]` (the
canonical transcript) plus `sdkSessionId` (a UUID pointing to Claude Agent SDK's
per-session JSONL file in `~/.claude/projects/<cwd-hash>/<uuid>.jsonl`). The SDK
prunes these JSONL files on a rolling schedule, so `sdkSessionId` can become stale.

When `sdkSessionId` is present but the corresponding JSONL file has been pruned, the
SDK's `resume` path throws:

```
No conversation found with session ID: <uuid>
```

This made affected chats permanently non-continuable — any send attempt hit the error
and the user had no recovery path.

## Decision

### 1. Two-layer session-existence guard

**Pre-flight check (FR-001):** Before setting `QueryOptions.resume`, call
`getSessionInfo(sessionId, { dir: workspaceRoot })`. If it returns `undefined`, the
session is absent; arm `needsReseed = true` and skip setting `resume`. The query
then starts a fresh SDK session from scratch using the synthetic-history iterator.

**Runtime catch (FR-002):** If `query()` still throws "No conversation found with
session ID" (e.g. race condition where the file disappears after pre-flight), catch
the error, reset all partial streaming state, send `agent:init` to clear renderer
state, rebuild the reseed iterator, and retry `query()` exactly once. If the retry
succeeds, `reseededSuccessfully = true` and the error is not surfaced; if it fails,
the error propagates normally.

Both layers live in `liminis-app/src/main/claude-agent.ts` (`ClaudeAgentManager.run()`).

### 2. Reseed iterator — `buildReseedMessageIterator`

`liminis-app/src/main/agent/reseed-history.ts` exports an `AsyncGenerator` that
converts `ConversationEntry[]` into a stream of `SDKUserMessage` values:

| Entry type | SDK message emitted |
|---|---|
| `UserEntry` | `{ role: 'user', content: text }`, `shouldQuery: false`, `isSynthetic: true` |
| `TextEntry` | `{ role: 'assistant', content: text }`, `shouldQuery: false`, `isSynthetic: true` |
| `ToolCallEntry` | `{ role: 'user', content: "[Tool call: name(input) → result]" }`, `shouldQuery: false`, `isSynthetic: true` |
| All others | Skipped (ThinkingEntry, ErrorEntry, SystemEntry, app-specific entries) |

The final real user message is yielded last without `shouldQuery: false`, causing
the SDK to actually query the model.

`MAX_RESEED_ENTRIES = 200` caps the number of prior entries replayed. Entries beyond
this limit are dropped from the oldest end to avoid context-window budget errors.

### 3. `priorEntries` threaded from `RunAgentOptions` through `AgentRunOptions`

`chat-state-manager.ts` passes `priorEntries` to the agent runner in `processMessage()`:
- Normal chat: `priorEntries = [...state.entries]` (the full chat history so far).
- Sidebar first message: `priorEntries = parentState.entries.slice(0, branchIdx + 1)`
  — the parent's history up to the branch point. This also covers the case where the
  parent's SDK session is absent, which previously required a live `parentSdkSessionId`
  (see ADR-065 amendment below).

### 4. ADR-065 amendment — sidebar creation no longer requires live parent session

The guard `if (!parentState.sdkSessionId) throw new Error(...)` in `createSidebar()`
has been removed. A sidebar can now be created from any chat regardless of whether its
parent's SDK session is alive. On first message, `processMessage()` determines
whether to fork (if `parentSdkSessionId` is live) or to reseed (if it is absent).

## Consequences

- **Chats become continuable after SDK session pruning.** The common user-facing
  breakage (re-opening an old chat and hitting "No conversation found") is eliminated
  for all chats that have durable `entries[]`.
- **Synthetic-history fidelity.** The reseed replays user/assistant turns faithfully.
  Tool calls are summarised as plain text rather than exact API content blocks — the
  model sees "what happened" but not the raw tool result structure. For most use cases
  this is adequate. If exact tool-result fidelity becomes important, the iterator can
  be extended to emit proper `tool_use`/`tool_result` content blocks.
- **No extra IPC or storage.** `priorEntries` is already in memory in
  `chat-state-manager` and is serialisable (used for persistence already).
- **Reseed on every pruned session** means one extra `getSessionInfo` RPC per agent
  run. This is O(1) and fast (file-stat equivalent); the cost is negligible.
- **`MAX_RESEED_ENTRIES = 200`** is a pragmatic ceiling. Very long chats will lose
  their oldest context, which is the correct tradeoff (a partial context is better
  than an error).
- **Pre-reseed checkpoints are unrestorable.** After a successful reseed, the chat
  has a new `sdkSessionId`. Any existing checkpoints in `chatState.checkpoints[]` still
  reference the old (pruned) session and cannot be restored via `rewindToCheckpoint()`.
  This is a known limitation; checkpoint restoration after reseed is deferred as a
  follow-up. The user is not notified, since checkpoints are an internal mechanism.
