# ADR-066: Prebuilt CoreML Embedding Asset Distribution

**Date:** 2026-06-22
**Status:** Accepted
**Issue:** #874

## Context

The CoreML embedding assets — `bge-base-en-v1.5.mlpackage` (~208 MB uncompressed) and the
offline HuggingFace tokenizer cache — are produced by running `convert-embedding-model.py`
and `prepare-tokenizer.py` via `uv run` (torch 2.4.0 + coremltools 8.1). They
are gitignored and regenerated on every fresh checkout.

Prior to this change, `uv` was a hard prerequisite of `pnpm bootstrap` even
when assets were already staged, and the release pipeline (`release.yml`) had
no step to produce assets before calling `pnpm package`, making it silently
broken on a fresh CI runner. The conversion is a deterministic, one-time,
hardware-agnostic step — the `.mlpackage` is a portable container; CoreML
selects the execution unit (CPU/GPU/ANE) at load time on the target device.
There is no reason to run this conversion on every developer machine or in
every CI build.

## Decision

Introduce a three-tier fetch-first architecture:

1. **CI Producer** (`build-embedding-assets.yml`): a macOS arm64 CI job
   triggered by changes to the conversion scripts or `workflow_dispatch`.
   It runs `prepare-embedding-assets.sh` with the pinned toolchain
   (`UV_NO_CACHE=1` for determinism), packages the output as
   `embedding-assets-<version>.tar.gz` with a SHA-256 sidecar, and publishes
   both to a GitHub Release tagged `embedding-assets-<version>`.

2. **Fetch Consumer** (`fetch-embedding-assets.sh`): a pure-bash downloader
   (only `curl`, `shasum`, and `python3`, no `gh` CLI required) that downloads,
   verifies, and stages the tarball (sentinel written last so partial failures
   are always detected). Uses the GitHub API asset endpoint
   (`GET /repos/{owner}/{repo}/releases/assets/{id}` with
   `Accept: application/octet-stream`) rather than the public browser-download
   URL — the browser-download URL 404s on private repos even with a valid token.
   Asset IDs are resolved via `GET /repos/{owner}/{repo}/releases/tags/{tag}`
   (JSON parsed with `python3`). Called by `dev-bootstrap.sh` on the default
   path and by `release.yml` before `pnpm package`. Skips if the
   `.embedding-asset-version` sentinel already matches.

3. **Version Gate** (`check-embedding-assets.sh`): extended to compare a
   `.embedding-asset-version` sentinel file against a hardcoded
   `EXPECTED_ASSET_VERSION` constant. Presence checks run first (missing assets
   → actionable error), then version check (stale assets → loud failure). A
   SHA-256 of the weight file is not recomputed on every check; integrity
   is verified once at fetch time.

### Version key format

`bge-<rev8>-coreml<X>-torch<Y>` (e.g., `bge-a5beb1e3-coreml8.1-torch2.4.0`).
Human-readable and stable across format changes. `check-embedding-assets.sh`
is the single source of truth; the CI workflow reads it via grep, and
`fetch-embedding-assets.sh` duplicates it with a "must match" comment.

### GitHub Release tag naming

`embedding-assets-<EXPECTED_ASSET_VERSION>` on `verveguy/liminis`. Dedicated
tags decouple the asset build cycle from the `v*.*.*` app release cycle.

### `uv` scope

`uv` is now **CI-build-only**: required in `build-embedding-assets.yml` and
for `pnpm bootstrap --refresh-assets`, but not for the default bootstrap or
release packaging path.

## Version bump procedure

When bumping `PINNED_BGE_REVISION` or the coremltools/torch toolchain pins:

1. Update `PINNED_BGE_REVISION` in `convert-embedding-model.py` and
   `prepare-tokenizer.py`.
2. Update `EXPECTED_ASSET_VERSION` in `check-embedding-assets.sh` and
   `EXPECTED_VERSION` in `fetch-embedding-assets.sh` (both constants must match).
3. Run `pnpm bootstrap --refresh-assets` locally (requires `uv`) to verify the
   new conversion produces valid assets.
4. Push to a branch and merge. The `build-embedding-assets.yml` CI job
   auto-triggers on merge to `main` and publishes the new artifact.
5. All subsequent `pnpm bootstrap` and `pnpm package` runs fetch the new artifact.

## Bootstrapping constraint

Between the PR merge and the first successful `build-embedding-assets.yml` run,
the GitHub Release tag does not yet exist. Any `pnpm bootstrap` or `pnpm package`
on a clean machine will fail at the fetch step. Mitigations:

- Trigger `build-embedding-assets.yml` via `workflow_dispatch` immediately after
  the PR merges.
- If needed, any developer with `uv` can unblock themselves with
  `pnpm bootstrap --refresh-assets` in the meantime.
- The error message in `fetch-embedding-assets.sh` directs to both options.

## Alternatives Considered

1. **Commit assets to git-lfs**: Rejected — adds repo size permanently; clone
   latency grows with every model version. GitHub Releases are on-demand.
2. **Download model on first app launch**: Rejected (see ADR-061 Alternatives).
   Distribution via the prebuilt Release artifact is the same principle applied
   to the developer tooling layer.
3. **Use `gh release download` instead of curl**: Rejected — requires `gh` CLI
   installed on developer machines. `curl` + `shasum` + `python3` are present
   on macOS by default (Xcode CLT, which is already required for `swift build`,
   provides all three). `python3` is used for JSON parsing to extract asset IDs
   from the GitHub API response; `awk`/`sed` are fragile for JSON and BSD `grep`
   lacks Perl regex (`-P`), making them unreliable for this purpose.
4. **Use `jq` for JSON parsing**: Rejected — not present by default on macOS or
   standard CI runners; requires a separate install step. `python3` is
   already guaranteed by the Xcode CLT prerequisite.

## Consequences

**Positive:**
- Fresh checkout → working app with no `uv`/Python installed (SC-001).
- Release pipeline works on a clean CI runner with no conversion step (SC-002).
- Stale or corrupt assets are caught loudly at bootstrap and package time
  (SC-004, FR-006).
- Model version bumps are a one-push operation; CI handles the artifact
  publication automatically.

**Negative:**
- Between PR merge and first `workflow_dispatch` there is a bootstrapping window
  where fetch will fail. Documented above.
- Developers who have locally generated assets without a `.embedding-asset-version`
  sentinel (pre-874 builds) will trigger an automatic re-fetch (~50 MB).
- `GITHUB_TOKEN` with `repo` read scope is **mandatory** while this repository
  is private. The public browser-download URL (`releases/download/{tag}/{file}`)
  always returns 404 for private repos even with a valid token; only the GitHub
  API asset endpoint works, and it requires authentication. A `public_repo`-only
  token is not sufficient. If/when the repo becomes public, the API-endpoint
  method remains valid and no migration is needed.
